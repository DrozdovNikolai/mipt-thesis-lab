# «55 Север»: спецификация модуля анализа речи экипажа

Версия: 1.0 · Дата: 13.09.2026 · Название Python-пакета: `north55_speech`.

**Это задание на реализацию, а не описание уже существующего решения.** Код, модели, датасеты и результаты экспериментов вместе с этим документом не предоставляются. Все целевые значения ниже — проектные критерии приёмки, а не достигнутые показатели и не отраслевые нормативы.

## 0. Цель и обязательные ограничения

Реализовать самостоятельный Python-модуль, который принимает запись разговора экипажа и инструктора внутри кабины/тренажёра и создаёт проверяемый черновик цифрового журнала. Параллельно построить воспроизводимый экспериментальный стенд, позволяющий доказать улучшение распознавания по сравнению с заранее зафиксированным Whisper baseline.

Продуктовый контекст из предоставленного плана: анализ речи тренажёрной сессии, журнал инструктора, проверка AI-контура через фиксированный набор, эталонную разметку, WER и precision/recall/F1. Новые технические решения и численные критерии этого документа предложены для реализации; их не следует выдавать за требования университета из исходного плана.

Обязательные ограничения:

- Предметная область — **cockpit / simulator / crew communication, НЕ pilot–ATC радиообмен**. Наличие слова «pilot» в названии корпуса не делает его подходящим.
- Python 3.11 как исходная целевая версия. При подтверждённой несовместимости выбранных библиотек разрешена согласованная смена minor-версии с записью причины в ADR. Развёртывание, импорт, обучение, тесты и оценка — через Docker Compose.
- Поддержать EN, RU и режим смешанной речи. Поддержка входного языка не равна доказанному качеству на нём. FR/DE допускаются в дополнительных корпусах, но не заменяют проверку RU.
- Локальная обработка по умолчанию. Никаких обязательных платных API, облачной транскрибации или отправки записей внешним сервисам. Сеть допускается на явном этапе получения зависимостей, весов и разрешённых данных.
- Не обучать большую ASR-модель с нуля. Реальные адаптеры готовых моделей, собственная обработка, обучаемый классификатор и строгая оценка — достаточная основа проекта.
- Нельзя обещать статистическое улучшение до эксперимента. Задача разработчика — добиваться его на development-данных и проверить на закрытом test. **Без подтверждения улучшения исследовательская приёмка не пройдена.**
- Отсутствие данных/GPU/доступа не разрешает подменять результаты заглушками. Разделять `implemented`, `executed`, `verified`, `blocked` для каждого компонента.
- Существующий репозиторий, пользовательские изменения, `AGENTS.md` и секреты сохранять. Не переписывать приложение «55 Север» целиком. При отсутствии репозитория создать самостоятельный проект с REST-интеграцией.

Приоритет: корректность данных и метрик → работающий сквозной сценарий → объективное улучшение → дополнительные возможности. Ни один модуль не должен считаться улучшением только потому, что он добавлен в цепочку.

## 1. Пользовательский сценарий и границы продукта

Инструктор загружает файл, указывает язык/автоопределение и при необходимости соответствие каналов участникам. Система возвращает `session_id` и `job_id`, обрабатывает запись в очереди, сохраняет транскрипт с таймкодами и черновик событий. В интерфейсе можно прослушать исходный фрагмент, увидеть риск ошибки, назначить роли говорящим, исправить текст/категорию и подтвердить запись журнала.

Результат — материал для разбора тренировки, а не управление воздушным судном, сертифицированный контроль безопасности или автоматическая оценка квалификации пилота.

Фраза «Gear down» доказывает наличие произнесённой фразы, но не доказывает фактический выпуск шасси. Фраза «We're too high» — сообщение участника, а не подтверждённое телеметрией отклонение. Не выводить `ERROR`, нарушение SOP, состояние самолёта, причину происшествия или оценку пилота без соответствующих источников и отдельной валидации.

Непрерывная обработка в реальном времени, видеоданные, автоматическое диагностирование стресса, корпоративная многопользовательская система и управление тренажёром не входят в первую версию.

## 2. Архитектура и стек

Не создавать микросервис на каждый ML-этап. Использовать общий пакет с типизированными интерфейсами и два основных Python-процесса — API и worker.

| Компонент | Предлагаемое решение | Ответственность |
|---|---|---|
| API и небольшая UI | FastAPI, Pydantic v2, Jinja2, минимальный локальный JavaScript | Загрузка, статус, просмотр аудио и журнала, review, экспорт |
| Фоновые задачи | Celery + RabbitMQ | Выполнение длительных задач, подтверждения доставки, повтор временных сбоев |
| Метаданные | PostgreSQL, SQLAlchemy 2, Alembic | Сессии, задания, результаты, аудит, registry версий |
| Большие файлы | Docker volumes / разрешённые bind mounts | Исходное аудио, промежуточные артефакты, датасеты и модели |
| Аудио | FFmpeg/ffprobe, soundfile, NumPy, SciPy | Проверка, декодирование, ресемплинг, работа с каналами |
| VAD | Silero VAD, предпочтительно ONNX для базового CPU-образа | Речевые интервалы |
| ASR | faster-whisper / CTranslate2 | Локальная транскрибация Whisper |
| Диаризация | адаптер локальной pyannote `speaker-diarization-community-1` | Говорящие и наложения речи; отдельная опция с доступом к весам |
| NLP | scikit-learn: TF-IDF + OneVsRest LogisticRegression | Обучаемая multi-label классификация эпизодов |
| Метрики | jiwer, scikit-learn, собственные entity/event scorers | WER/CER, классификация, сущности, события |
| Эксперименты | CLI на Typer, YAML-конфигурации, JSON/CSV/Markdown/HTML | Подготовка данных, сравнения, quality gate |
| Качество кода | pytest, Ruff, mypy, интеграционные тесты | Проверка контрактов и регрессий |
| Зависимости | pyproject.toml + lockfile, например uv.lock | Воспроизводимая установка |

MLflow, Redis, MinIO, Kubernetes, Grafana, внешний LLM и отдельный frontend-framework не нужны для обязательного контура. Не добавлять их «на всякий случай».

faster-whisper документирует CPU/GPU-исполнение, таймкоды слов и интеграцию Silero VAD; конкретные параметры необходимо проверять для закреплённой версии [S2, S3]. В модели pyannote есть отдельные условия доступа к весам; не обходить их [S4].

## 3. Docker Compose и запуск

### 3.1. Сервисы

`compose.yaml` — рабочий CPU-вариант:

- `api`: один лёгкий API-процесс без загруженной ASR-модели. UI обслуживается им же.
- `worker`: Celery worker, начальная concurrency=1, модель переиспользуется между заданиями.
- `postgres`: постоянный volume, healthcheck; служебные порты наружу не публиковать.
- `rabbitmq`: постоянный volume, durable queues; management UI по умолчанию не публиковать.
- `migrate`: одноразовый запуск Alembic после готовности БД; API/worker стартуют после успешной миграции.
- `tools`, profile `tools`: одноразовые CLI-команды импорта, подготовки моделей, тестов, development-экспериментов и отчётов.
- `evaluator`, profile `eval`: отдельный CLI scorer, имеющий доступ к тестовым эталонам. Обычные inference-процессы не должны получать reference_text/event labels.
- `trainer`, profile `training`: обучение классификатора; отдельный train-image/extra для опционального Whisper LoRA.

`compose.gpu.yaml` — override существующего `worker` и необходимых tools/trainer, а не второй конкурирующий worker на ту же очередь. GPU выдать через поддерживаемую Compose device reservation. Указать `capabilities: [gpu]`; проверить совместимость host driver/container runtime/CUDA/cuDNN/CTranslate2 [S2, S5].

Не использовать `latest`. На этапе реализации закрепить реально проверенные образы и версии; не выдумывать digest или номера релизов. CPU-образ не должен требовать NVIDIA-драйвер. GPU-зависимости обучения и inference разрешается изолировать разными образами.

### 3.2. Хранилища

`postgres_data`, `rabbitmq_data`, `audio_data`, `artifact_data`, `model_cache`. Корпусы отдельно в `data/raw`, `data/curated`, `data/manifests`; отчёты — `reports/`. Исходные записи и модели не включать в git и image layers.

Веса загружаются явной CLI-командой с manifest/checksum/revision, затем runtime читает локальные файлы. При отсутствии модели возвращать `MODEL_NOT_AVAILABLE`, а не незаметно скачивать другую модель или генерировать фиктивный транскрипт.

Для test-оценки отделить inference-manifest без ответов от sealed references. Training/dev не монтируют тестовые эталоны. Это организационная и техническая защита от случайной утечки, не обещание криптографической изоляции от владельца Docker-хоста.

### 3.3. Требуемые команды после реализации

Подготовить инструкции для PowerShell/Windows Docker Desktop и Linux. Host Python, Make, CUDA Toolkit на Windows-хосте для CPU-сценария не нужны. Наличие совместимого Docker и, для GPU-сценария, корректной GPU-среды проверяется отдельно.

```sh
# После создания .env из .env.example и генерации локальных секретов:
docker compose build
docker compose --profile tools run --rm tools assets fetch --preset cpu-demo
docker compose up -d
docker compose --profile tools run --rm tools doctor
docker compose --profile tools run --rm tools demo --real-asr

# GPU: те же сервисы с override
docker compose -f compose.yaml -f compose.gpu.yaml up -d --build
```

`doctor` проверяет доступность БД/брокера, миграции, volumes, FFmpeg, версии библиотек, модели, offline-ready состояние и фактическую видимость GPU. Сообщение «GPU проверен» допустимо только после реального inference.

`.env.example` не содержит действительных токенов. Предоставить `scripts/bootstrap.ps1` и `scripts/bootstrap.sh`, которые не перезаписывают имеющийся `.env` и создают случайные локальные секреты без установки host Python. Локально публиковать только `127.0.0.1:8000`.

## 4. Контракты конвейера

```text
Upload / local dataset importer
  → immutable original + hash + provenance
  → audio validation / channel handling / resampling
  → VAD + mapping to original timeline
  → optional empirically selected denoising
  → multilingual ASR + timestamps
  → optional diarization / explicit channel-speaker mapping
  → conservative display normalization + evidence spans
  → contextual episodes
  → event classifier + entity extraction
  → review-risk assessment
  → draft instructor journal + exports
```

Порядок VAD/denoise — параметр экспериментальной конфигурации: по умолчанию VAD на исходном подготовленном сигнале, denoise — только в ASR-ветви. Диаризация может идти параллельно ASR и объединяться по исходной временной шкале. Не уничтожать исходные каналы ради единственной mono-версии.

Общие интерфейсы: `AudioPreprocessor`, `VadProvider`, `AsrProvider`, `DiarizationProvider`, `TextNormalizer`, `EpisodeBuilder`, `EventClassifier`, `EntityExtractor`, `ReviewPolicy`, `JournalBuilder`. Для каждого — вход/выход Pydantic-модель, version/config hash, типизированные ошибки, длительность и артефакты.

Два режима обязательны:

- `baseline`: общий корректный decode/resample и зафиксированный ASR без доменных улучшений.
- `candidate`: та же ASR-модель и вычислительная точность, выбранные дополнительные этапы.

Добавление событий в журнал само по себе не считается улучшением WER. Замену small на large показывать отдельным model-comparison, а не приписывать эффект предобработке.

## 5. Входное аудио, каналы и временная шкала

Принимать WAV, FLAC, MP3, M4A, OGG при фактической поддержке закреплённого декодера. Проверять контейнер и декодируемость, а не только расширение. Настраиваемые начальные лимиты: 2 GiB на файл, 4 часа, не более 8 каналов. Невалидный файл, превышение лимита, отсутствие дорожки, исчерпание диска — разные ошибки.

Сохранить исходные байты и SHA-256. Рабочий ASR-сигнал — PCM/float32 16 kHz; mono создавать только для нужной ветви. Сохранять sample rate, channels, duration, исходный offset, clipping/peak/RMS diagnostics. Не нормализовать тишину делением на ноль и не увеличивать уровень шума бесконтрольно.

Режимы каналов:

- `mixed`: разговор в общей дорожке, диаризация по необходимости.
- `separate_channels`: распознавать каналы отдельно, сохранить speaker/channel evidence и общую шкалу времени.
- `explicit_mapping`: роли каналов предоставлены пользователем или подтверждёнными метаданными.

Нельзя считать left=КВС, right=второй пилот по умолчанию. Crosstalk отмечать; не дублировать один и тот же звук как две разные реплики без проверки. Не удалять действительно повторённую команду ради красивого транскрипта.

Для VAD cuts, chunk overlaps и ресемплинга хранить обратимое отображение к исходным sample offsets. Таймкод `start_sec` в журнале всегда относится к оригинальной записи. Хранить word timestamps при наличии, но не выдавать их за точную фонетическую разметку.

## 6. VAD, шумоподавление и распознавание

### 6.1. VAD

Реальный Silero-адаптер, параметры threshold/min_speech/min_silence/padding/max_chunk_length в YAML. Начальные значения — настраиваемые гипотезы, не «авиационно оптимальные» константы. Добавлять padding, сохранять короткие callouts, тестировать начало/конец слова и единичные короткие реплики.

Не применять два независимых VAD молча: внешний VAD означает явное отключение внутреннего либо документированное использование единого механизма. Не склеивать весь час в одну непрерывную речь и не терять паузы/offsets. Отсутствие речи — корректный пустой результат, не исключение и не повод выдумать текст.

### 6.2. Denoise

Реализовать identity/pass-through и одну реальную воспроизводимую спектральную обработку, например conservative spectral gating на SciPy. Отдельно хранить параметры, источник оценки шума, задержку и обработанный файл. Нельзя оценивать шум с помощью тестовой расшифровки или чистой paired-reference записи, недоступной при эксплуатации.

Denoise выключен в baseline и не включается в release без dev-обоснования и общего test gate. Если он ухудшает критические числа/тихие согласные, исключить его из выбранного конвейера. Наличие реализации не означает, что stage обязан быть активен.

### 6.3. ASR

CPU smoke/demo: multilingual Whisper `small`, int8. Основной GPU-эксперимент: первоначальный кандидат `large-v3`, float16 либо int8_float16 при проверенной совместимости и зафиксированном общем выборе. Профили и реальные revisions записываются в `models.lock.json`. Это настройки задания, а не обещание достаточной памяти на неизвестном железе.

Для честного сравнения baseline/candidate использовать одинаковые checkpoint, quantization, decoder backend, язык/доступные входные метаданные и общий preprocessing. Baseline должен быть разумно настроен, а не искусственно испорчен: исходно beam_size=5, temperature=0, task=transcribe; все остальные существенные параметры также явно фиксируются.

Проверить реальные параметры версии: `initial_prompt`, `hotwords`, `condition_on_previous_text`, language detection, word timestamps [S2a]. Не предполагать, что batched и обычный `transcribe` одинаково применяют все опции. Для каждого экспериментального фактора логировать effective config; неиспользуемый параметр — ошибка конфигурации.

RU/EN/mixed:

- `language=ru/en` — явное пользовательское указание; одинаково доступно обеим системам.
- `language=auto` — определение по аудио, не по reference_text.
- `language=mixed` — многоязычный режим/сегментная стратегия с контекстом и возможностью `unknown`; короткое английское слово внутри русской фразы нельзя насильно переводить на русский.
- Не использовать `task=translate`. Не подменять поддержку RU англоязычным distilled checkpoint.

Доменный контекст — небольшой versioned glossary и список терминов/сокращений, а не ожидаемый транскрипт конкретной записи. Его источники: публично разрешённые материалы и train/development. Запрещены тестовые ответы, приватные annotations, sample-specific numeric values из эталона и retrieval по идентификатору тестового файла.

Для сомнительного сегмента допускается ограниченная повторная транскрибация с иной разрешённой конфигурацией. Правило её запуска и выбора гипотезы учится/фиксируется на development; эталон в production-селектор не передаётся. max_redecode_passes=1 как исходный лимит. Если две гипотезы расходятся по критическому значению, сохранять disagreement и отправлять на review, а не выбирать более «правдоподобное» число.

## 7. Диаризация и роли

Поддержать `off`, `channel_mapping`, `pyannote_local`. Адаптер pyannote должен реально исполняться при доступных весах; gated-модель не скачивается без принятия условий/токена владельцем. Использовать минимально необходимый read-доступ и не записывать токен в image/логи.

Без доступной диаризации возвращать `speaker_id=null` или подтверждённую метку канала и `component_status=blocked/not_requested`; не придумывать Speaker 1/2. Отсутствие весов не ломает ASR и журнал.

Автоматические идентификаторы `SPEAKER_00`, `SPEAKER_01` действуют внутри одной записи. Они не устанавливают личность и роль. Роль `captain/first_officer/instructor/unknown` назначается явно с provenance; акустический тембр не основание для роли.

Сохранять overlapping turns. При неоднозначном сопоставлении слова и говорящего возвращать uncertainty/overlap, не давать ложной уверенности. Диаризацию оценивать DER/JER только при существующей speaker/time-разметке; описание протокола (collar, overlap handling) обязательно.

## 8. Нормализация, сущности и запрет скрытого исправления

Хранить три раздельные сущности: `raw_asr_text` (неизменяемый вывод модели), `display_text` (безопасное форматирование), `reviewed_text` (явное человеческое исправление с аудитом).

Разрешённая нормализация: Unicode, пробелы, регистр для поиска; прозрачные обратимые варианты написания терминов. Число «fifteen» можно представить как 15 в структурированном поле, только если именно это однозначно распознано. `fifty → fifteen`, `tree → three` не являются безусловно безопасными правилами и не должны происходить глобальной заменой. Список допустимых положений закрылков не даёт права переписать аудио под него.

Отрицания, единицы, десятичные разделители и направление (`above/below`, `up/down`) сохранять. Не выводить скорость/высоту без указания единиц из ничего: `unit=null` при их отсутствии. Не превращать «speed 160» в доказанную фактическую скорость.

Каждое изменение: old/new, rule_id, source spans, justification, version. Исходный текст всегда доступен. Для WER использовать отдельный симметричный evaluator-normalizer, а не цепочку отображения результата.

Сущности первоначально извлекать детерминированным типизированным parser:

`flaps_setting`, `gear_position_mention`, `speed_mention`, `altitude_mention`, `heading_mention`, `checklist_name`, `warning_mention`.

Обязательны `surface`, `canonical_value`, `unit`, `polarity`, `source_segment_id`, `source_span`, `start_sec/end_sec`, `certainty_kind`, `evidence_kind=speech`. Неоднозначный разбор возвращает alternatives/needs_review или null, не выдуманное значение. Для числовых сущностей тестировать EN, RU, mixed и «fifteen/fifty», «one six zero/one sixty», русские окончания, отрицание, отсутствующие единицы.

## 9. Эпизоды и классификация

### 9.1. Построение эпизодов

Начать с воспроизводимых правил объединения соседних реплик: разрыв по паузе, максимум длительности/токенов, граница speaker turn, ограниченный предыдущий/следующий контекст. Все thresholds задаются в YAML и подбираются на development. Сохранять IDs исходных реплик и точные границы.

Flight phase — отдельное необязательное поле `taxi/takeoff/climb/cruise/descent/approach/landing/unknown`. В отсутствие телеметрии и соответствующей разметки использовать только explicit verbal cue с `phase_source=speech_hint` либо `unknown`. Не обещать восстановление всех этапов полёта по любому короткому файлу. Реализовать интерфейс импорта подтверждённой phase-разметки из тренажёра на будущее, не выдавать её за предсказание модели.

### 9.2. Таксономия

Multi-label схема: одна реплика может относиться к нескольким категориям.

| Код | Что размечается |
|---|---|
| `CHECKLIST` | Чтение/запрос/ответ в чек-листе |
| `CONFIGURATION_MENTION` | Упоминание/команда изменения конфигурации |
| `REPORTED_DEVIATION` | Произнесённое сообщение об отклонении |
| `WARNING_MENTION` | Речевое упоминание предупреждения/проблемы |
| `CREW_COORDINATION` | Взаимодействие/согласование действий экипажа |
| `INSTRUCTOR_FEEDBACK` | Обратная связь инструктора при известной роли или достаточной разметке |
| `OTHER` | Ни один из целевых классов; не совмещать с ними |

Отдельные поля: `speech_act=command/readback/report/question/comment/unknown`, `salient_for_review=true/false/unknown`. Значимость размечается экспертом отдельно; нельзя автоматически считать любое `OTHER` незначимым или любое `CHECKLIST` значимым.

### 9.3. Реализации

`rules_v1` — честный базовый классификатор на небольшой фиксированной совокупности правил.

`tfidf_logreg_v1` — **реально обучаемая модель**: word n-grams + char n-grams, TF-IDF/FeatureUnion, OneVsRest LogisticRegression [S11], настройки imbalance, seed, thresholds по классам. Vectorizer.fit выполняется только на train. Сохранять pipeline artifact, schema/ontology version, train/dev hashes и metrics. Загружать только собственные доверенные сериализованные модели, не пользовательский pickle.

Подготовить команды `train events`, `evaluate events` и сравнение с rules. Нельзя считать модель обученной, если выполнен только constructor. При отсутствии независимой человеческой event-разметки rules остаётся явно помеченным baseline, а обучаемая модель получает `blocked: missing_event_labels`.

Эталонный ASR-транскрипт не содержит автоматически эталонных событий/значимости. Метки из собственных rules или LLM могут быть weak labels для train, но не независимым ground truth для test. Синтетические примеры проверяют код, не доказывают качество распознавания реального разговора.

## 10. Review, confidence и журнал

ASR log-probability, no_speech probability, disagreement и confidence классификатора не являются одной универсальной вероятностью правильности. По умолчанию хранить раздельные сигналы и `risk_level=low/medium/high/unknown`. Любой объединённый score пометить `heuristic_uncalibrated`.

Калиброванную вероятность вводить только при отдельной calibration-разметке из development; зафиксировать calibrator и оценить Brier/reliability на held-out данных [S7]. Значение 0.97 нельзя представлять как «97% верно» без такой проверки.

Причины review: расхождение чисел, низкое качество аудио, overlap, неуверенный speaker, неподтверждённая единица, обрезанный фрагмент, низкий classifier margin, неподдержанный язык. `needs_review` не исключает пример из автоматической оценки: пропуск остаётся пропуском.

Весь журнал первоначально `draft`. Подтверждение instructor review меняет workflow-status, но не делает запись источником фактической телеметрии. Каждая строка содержит время, speaker/role при наличии, категорию, цитату, сущности, evidence links, risk reasons, версии и состояние проверки. Автоматическое резюме — template-based по найденным событиям; обязательный LLM не нужен.

Исправления сохранять отдельной ревизией с before/after, временем, автором и причиной. Не перезаписывать результаты прошлых benchmark и не превращать исправления текущего test в train той же версии.

## 11. Данные, импорт и аннотации

### 11.1. Кандидаты, а не гарантированно готовые зависимости

Упомянутые в обсуждении BLeRIOT-A, BLeRIOT-C, HIWIRE, VOICI noise, русские авиационные команды — **кандидаты для проверки**, а не уже скачанный и проверенный набор. Проверка существования публикации не заменяет проверку лицензии, WAV, transcript alignment и возможности исключить ATC.

Сначала реализовать универсальный local importer (`audio + JSONL/CSV transcript + metadata`) и manifest validator. Специализированный адаптер писать после проверки реальной структуры файлов; не придумывать имя ZIP/JSON-поля/прямой download endpoint. Недоступный источник помечать `blocked`, работа с локальным форматом продолжается.

Сведения о кандидатах и статус текущей проверки перечислены в `SOURCES.md`. Автоматическая загрузка только при подтверждённых URL, разрешении, размере в установленном бюджете и checksum. Платные HIWIRE/SUSAS или запросы авторам не выполнять автоматически.

### 11.2. Data card и фильтрация

Для каждого источника сохранить: происхождение, лицензия/условия/attribution, download date, version/revision, список файлов и hashes, языки, авторство транскриптов, real/read/synthetic speech, cockpit/ATC scope, train restrictions, known limitations.

Сегменты маркировать `scope=cockpit/simulator/read_cockpit/atc/unknown`. Для основной проверки разрешены только проверенные не-ATC данные; смешанный CVR-файл требует сегментной разметки. Удаления из-за scope фиксируются **до просмотра ошибок сравниваемых моделей**. Нельзя фильтровать «неудобные» записи после результатов.

Noise-only корпус не оценивается как обычный speech-to-text test с ненулевым эталоном. Corpus с одним голосом/озвученными командами не доказывает диаризацию и распознавание естественного crew dialogue. Text-only CVR полезен для NLP при подходящих метках, но не для WER.

### 11.3. Канонический manifest

Ниже схема записи, не реальные данные и не заданные значения модели:

```json
{
  "sample_id": "opaque-uuid",
  "audio_path": "audio/opaque-uuid.wav",
  "audio_sha256": "computed-sha256",
  "source_dataset": "local_cockpit",
  "source_version": "v1",
  "recording_id": "recording-uuid",
  "session_id": "session-uuid",
  "original_utterance_id": "source-utterance-uuid",
  "speaker_ids": ["pseudonym-01"],
  "script_id": null,
  "language": "en",
  "scope": "simulator",
  "speech_origin": "recorded_human",
  "acoustic_condition": "original",
  "variant_of": null,
  "duration_sec": 6.2,
  "channel": 0,
  "license_id": "local-consent-v1",
  "annotation_status": "human_verified",
  "reference_text": "reference supplied by annotator",
  "critical_entities": [],
  "events": [],
  "group_id": "computed-group",
  "split": "assigned-before-training"

```

`null`/отсутствие annotation и пустой подтверждённый список — разные состояния. `[]` разрешено как отрицательная разметка только при `annotation_status=human_verified` для соответствующей задачи. Разделять statuses для transcript/entities/events/diarization.

Проекция для inference содержит только audio locator, непрозрачный ID и реально доступные при эксплуатации metadata. Не передавать reference_text, labels, ground-truth language в auto-режиме, смысловые названия файлов или человеческие ответы через prompt.

### 11.4. Разделение и защита от leakage

До обучения строить `train/dev/test`, исходный ориентир 70/15/15 по группам, а не по случайным строкам. Все куски одной сессии/исходной записи и все clean/noisy/augmented варианты одного оригинала остаются в одном split. При наличии speaker IDs основной протокол — speaker-disjoint: связанные через общих говорящих сессии объединяются в группы.

Проверять пересечения SHA-256, canonical decoded-audio hash и parent/variant links. Для чтения повторяющихся длинных сценариев проверить script overlap и, когда возможно, выделить script-disjoint challenge. Одинаковая короткая естественная команда у независимых людей сама по себе не доказывает дубликат; правила text-dedup документировать, не объединять весь корпус через слово «checklist».

Если ограничения оставляют слишком мало независимых групп, не разрывать их ради процентов. Использовать grouped cross-validation только как development/exploratory результат либо сообщить о необходимости дополнительных независимых записей. Group-based evaluation и отдельный test предназначены для защиты от такого переобучения [S6].

Словари, scalers, модели, пороги, denoise policy и варианты pipeline не настраиваются на test. Возможное присутствие публичного корпуса в исходном pretraining Whisper не всегда проверяемо; не утверждать доказанную pretraining-disjoint оценку. Для сильного вывода о «55 Север» нужен отдельный разрешённый holdout из реального продукта.

Для основной агрегированной метрики заранее фиксировать один вариант на исходное utterance или фиксированные веса по акустическим условиям. Нельзя увеличивать вклад удобной записи множеством шумных копий. Для paired clean/noisy challenge использовать одних и тех же родителей и групповой bootstrap, показывая условия отдельно.

### 11.5. Аугментация шумом

При наличии законно доступного noise-only аудио создавать noisy variants уже после назначения split. Фиксировать родителя, noise_source, offset, seed, SNR, gain и итоговый hash. Масштабировать шум по active-speech RMS, не по произвольному RMS длинной тишины:

`alpha = rms(speech_active) / (rms(noise_active) * 10 ** (snr_db / 20))`.

Для предотвращения clipping допускается одинаковое масштабирование всей смеси с записью коэффициента; не менять SNR незаметно. Начальные экспериментальные уровни: clean, 20, 10, 5, 0 dB. Это **синтетически зашумлённая человеческая речь**, не реальные записи соответствующего полёта.

Разделять noise recordings между train/dev/test или явно указывать ограничение. Нельзя поместить BLeRIOT-A оригинал в train, а производный BLeRIOT-C вариант в test. Нельзя считать A/C matched-pair, пока связь не подтверждена metadata.

### 11.6. Инструменты разметки

В UI/CLI предусмотреть импорт и экспорт transcript/entity/event labels, таймкодов и speaker IDs; прослушивание фрагмента; отметку `unintelligible`; версию руководства по разметке. `docs/annotation_guide.md` определяет границы эпизода, числа/единицы, отрицания, значимость, overlap и спорные случаи.

Для части записей желательно независимое второе аннотирование и согласование разногласий; фиксировать фактически достигнутый объём и согласие, не выдумывать экспертов. Нельзя считать автоматическую расшифровку человеческим эталоном после изменения одного пробела.

## 12. Экспериментальный протокол и поиск улучшения

### 12.1. Заморозка baseline

Сначала проверить корректность baseline: правильный sampling rate, язык, модель, decoder, полный проход generator, отсутствие случайного перевода/обрезания. Затем сохранить `baseline.lock.json`: модель/revision/checksum, precision, effective decoder parameters, общая подготовка, hardware, версии runtime и evaluation normalization.

Baseline — не ослабленная игрушка. Запрещены неверный язык, tiny для baseline против large для candidate под видом «эффекта pipeline», неучтённый переход CPU/GPU/precision и специально плохие параметры.

### 12.2. Development-эксперименты

Обязательная таблица ablation:

| ID | Вариант | Что изолирует |
|---|---|---|
| A0 | Общая подготовка → frozen ASR | Исходный уровень |
| A1 | A0 + выбранный VAD/chunking | Сегментацию |
| A2 | A1 + ограниченный domain glossary/hotwords | Доменный контекст |
| A3 | A2 + denoise | Шумоподавление |
| A4 | A2 или A3 + limited re-decode | Обработку сомнительных фрагментов |
| A5 | Лучший вариант + обученная ASR-адаптация, если выполнена | Отдельный эффект fine-tuning |

Сравнивать также raw ASR text и display/canonical representation, но косметические изменения не засчитывать как улучшение основного lexical WER. Не требуется, чтобы A4 обязательно был лучшим: выбрать реально лучшую достаточно простую конфигурацию с guardrails.

Предусмотреть ограниченный поиск в `configs/search.yaml`: исходно не более 16 development-конфигураций, один дополнительный ASR-pass на сегмент. Пользователь может повысить ресурсный бюджет, но не постфактум ослабить acceptance thresholds. Для expensive training отдельные ограничения числа steps/epochs и объёма данных. Никакого бесконечного цикла «работать, пока цифра не станет зелёной».

Выбор candidate — детерминированная dev-policy: сначала допустимые guardrails, затем lexical WER, при сопоставимом качестве предпочтение более простому/быстрому pipeline. Зафиксировать tie-break до запуска поиска. Сохранить все попытки, включая ухудшения.

### 12.3. Обучение ASR как дополнительный реальный путь улучшения

Реализовать отдельно запускаемый train-path Whisper LoRA через Transformers/PEFT при законно доступных train/dev audio-transcript данных и подходящем GPU. Это не обязательное условие запуска API, но путь должен содержать настоящую загрузку данных, loss, optimizer, checkpoints, validation, early stopping и manifest, а не `pass`. Официальный пример PEFT/ASR можно использовать как отправную точку, адаптируя его к закреплённым версиям [S10].

До обучения проверить совместимость моделей/библиотек и формат конвертации. `faster-whisper` — inference backend: обучение выполнять другим поддерживаемым backend; затем корректно merge/adapt/convert модель и проверить её реальным inference. Эффект float precision/конвертации учитывать отдельной проверкой. Если LoRA не исполнялась, обозначить `implemented_not_executed` или конкретный blocker.

Не использовать test для early stopping. Ground truth noisy synthetic data допустим только как transcript того же исходного человеческого utterance с сохранением split. Не использовать голоса/данные без прав или клонирование голоса пилота.

### 12.4. Раздельная оценка NLP и всего конвейера

NLP-level: сравнить rules и trained classifier на одинаковых человеческих текстах/эпизодах. End-to-end: сравнить rules и trained classifier на одинаковом ASR-выводе, затем отдельно влияние baseline ASR против candidate ASR при одном frozen NLP. Это отделяет ошибку распознавания от ошибки классификации.

Для continuous recordings event matching выполнять по времени и классу, а не подавать классификатору истинные границы эпизодов в качестве «end-to-end». Если доступны только готовые utterances без session continuity, честно оценивать utterance classification, а качество поиска временных эпизодов помечать непроверенным.

### 12.5. Финальный test

До раскрытия test-ответов сохранить `selection.lock.json`: выбранный pipeline, checkpoints, glossary, thresholds, scorer version, primary cohort, языки, claimed labels, split/data hashes и hash acceptance config. `test_access_log.jsonl` фиксирует открытия/запуски.

Final-test — сравнение заранее выбранного candidate с A0 и заранее перечисленными контрольными вариантами. После просмотра результатов нельзя подкручивать pipeline и многократно объявлять ту же выборку «независимым финальным test».

Разрешено воспроизвести **тот же frozen run** для проверки повторяемости. Изменение модели/параметров после результатов требует нового независимого test или явного статуса exploratory; старый test больше не обосновывает новое подтверждающее утверждение. Исправление ошибки scorer допустимо только как документированный amendment с повторной симметричной оценкой всех систем, без подбора удачных изменений.

## 13. Метрики: точные определения

### 13.1. Распознавание

Основная метрика `wer_lexical = (ΣS + ΣD + ΣI) / ΣN`: корпусное отношение суммарных замен, удалений и вставок к числу слов в эталоне. Не усреднять WER коротких и длинных файлов без весов. Дополнительно выдавать per-file и group-macro значения.

`lexical_normalizer_v1` одинаков для hypothesis/reference: Unicode NFC, case-fold, контролируемая пунктуация/пробелы; не удалять отрицания, числа, единицы, направления или незнакомые слова. Десятичные знаки не уничтожать. Правила и тестовые примеры freeze до final test.

`wer_canonical` — дополнительная метрика с одинаковым числовым/терминологическим канонизатором на обеих сторонах. Не подменять ей основной WER, чтобы улучшение не свелось к `15 ↔ fifteen`. `cer` — дополнительная симметричная character-level метрика. Реализация WER/CER — через закреплённый jiwer с проверкой alignment и edge cases [S8].

При пустом reference не делить на ноль: считать число вставленных слов, долю ложных речевых сегментов и `inserted_words_per_non_speech_minute`. Невнятные spans исключать только по заранее размеченному одинаковому scoring mask. Если временные masks недоступны, применять явно описанный corpus-specific протокол; не скрывать неудобные слова.

ASR-failure/timeout candidate не удаляет sample из сравнения: для метрик считать пустую гипотезу и отдельно failure. В operational gate такие ошибки учитываются. `needs_review` также не удаляет слова из знаменателя.

### 13.2. Значимые сущности

Терминологический recall недостаточен: система может «улучшить» его, дописав весь авиационный словарь. Поэтому считать `CriticalEntityPrecision`, `Recall`, `F1` и ошибки числовых значений.

Эталон сущностей независимо human-verified и содержит конкретные вхождения, а не уникальные слова. Совпадение: type + canonical value + явно указанная unit + polarity, привязанные к тому же utterance/evidence interval. Для времени использовать versioned matching tolerance/правило. Повторные одинаковые вхождения матчить один-к-одному.

`critical_entity_error_rate = (C_sub + C_del + C_ins) / N_reference_entities`. Сначала детерминированно сопоставить упоминания по type/локальному span или временному якорю, затем сравнить value/unit/polarity. Неверное значение одного сопоставленного упоминания — одна замена, а не произвольное двойное наказание. Несопоставленные эталон/предсказание — deletion/insertion. Ошибки типа «flaps 50 вместо flaps 15» отдельно выводить в confusion table. Значение метрики может быть больше 1 — не обрезать.

Не строить ground-truth entities тем же непроверенным parser, который оценивается. Авторазметку можно использовать как заготовку с явной человеческой верификацией.

### 13.3. Классификация, значимость и события

Multi-label: per-label precision/recall/F1, macro-F1 по заранее объявленным labels, micro-F1, support и бинарные confusion matrices по каждому классу. Обычная единственная multiclass confusion matrix недостаточна. Классы без positive support помечать `not_evaluable`, а не приписывать им F1=1.

Значимость для разбора оценивать отдельным binary target на независимых labels. Начальные продуктовые targets: precision ≥ 0.80 и recall ≥ 0.85. `salient_for_review=unknown` не считается правильным negative.

Episode detection на целой записи: class-compatible one-to-one matching с temporal IoU ≥ 0.5, зафиксированный maximum matching, duplicates как false positives. Отдельно false positives per audio hour и missed events. IoU/порог фиксируются до test. При оценке только готовых utterances не называть результат «качество temporal episode detection».

### 13.4. Диаризация, время и ресурсы

DER/JER — только при speaker-time ground truth, с описанными collar/overlap. При отсутствии такой разметки `not_evaluated`, не нули.

Real-time factor `RTF = processing_wall_time / original_audio_duration`; указывать end-to-end и ASR-only, cold/warm, модель, CPU/GPU, precision, peak RSS/VRAM при доступном измерении, p50/p95, failure rate. Время получения весов/инициализации — отдельные значения. GPU и CPU throughput нельзя сравнивать как эффект алгоритма.

### 13.5. Неопределённость

Для сравнения WER — paired cluster bootstrap по независимой группе speaker/session, а не независимый bootstrap каждого noisy variant. Одни и те же sampled groups и weights у baseline/candidate; WER каждый раз пересчитывается через суммарные counts. Начально 2000 bootstrap samples, seed фиксирован, 95% percentile CI.

Определение `delta_wer = WER_candidate - WER_baseline`, поэтому улучшение отрицательно. Relative gain `(WER_baseline - WER_candidate) / WER_baseline`. При baseline WER=0 относительный target не вычисляется и нельзя автоматически выдать PASS.

Малое количество независимых групп и неизвестные speaker IDs ограничивают вывод. Минимумы в acceptance config — проектный фильтр от слишком слабой проверки, не математическая гарантия достаточной статистической мощности. Дополнительно выводить CI и фактический support по стратам.

## 14. Приёмка: engineering и доказанное улучшение

Исходный `ACCEPTANCE.yaml` входит в пакет задания. Реализация должна читать его и предоставлять JSON schema/валидацию. Скопировать без смысловых изменений в `configs/acceptance.yaml`, включить hash в freeze. Порог нельзя понижать после просмотра результатов ради зелёного отчёта.

### 14.1. ENGINEERING_GATE

PASS требует: валидные Compose CPU/GPU-конфигурации, успешные CPU integration tests, реальные ASR-адаптеры, работающий upload→queue→result→review→export, миграции, восстановление очереди, неизменяемое исходное аудио, корректные таймкоды и запреты опасных исправлений. GPU/dataset-specific тесты отдельно помечаются по фактическому исполнению; skip нельзя представлять как passed.

### 14.2. ASR_QUALITY_GATE

Начальный основной scope: human cockpit/simulator/read-cockpit EN, без ATC. RU/mixed полностью поддерживаются как входные режимы, но получают собственные `validated/unvalidated` статусы. Добавление языка в основной scope производится до freeze и до просмотра его test-results. EN-успех не доказывает RU/mixed.

Минимум для подтверждающего основного test: 20 независимых групп, 300 различных исходных human-recorded utterances (noisy-копии не увеличивают этот минимум), 3000 reference words, 100 независимо проверенных critical entity occurrences, отдельные clean control и non-speech controls. Это стартовые пороги достаточности для проекта; не гарантия репрезентативности продукта.

PASS требует одновременно:

1. Снижение `wer_lexical` не менее **10% относительно baseline** на заранее объявленном основном корпусе. Например, 30% → 27% — ровно 10% relative gain; это иллюстрация арифметики, не результат проекта.
2. Верхняя граница 95% CI для `delta_wer` меньше 0.
3. CriticalEntityF1 не ниже baseline, CriticalEntityErrorRate не выше baseline.
4. На отдельном clean-control рост lexical WER не больше **0.01 абсолютного значения**, то есть 1 процентного пункта. Такой же point guardrail для каждого языка заявленного validated scope.
5. На non-speech controls число вставленных слов в минуту не выше baseline. Данные, VAD-пропуски и sample failures не скрыты.
6. Нет необработанных runtime failures в frozen inference run и нет нарушений data/split/leakage checks.

Нельзя получить PASS на demo, TTS-only, ATC-only, неразмеченных или утекших данных. Read cockpit и синтетическое зашумление человеческой речи отчётливо отделять от спонтанного реального разговора. Область вывода — ровно фактически проверенная выборка.

### 14.3. NLP_QUALITY_GATE

Первоначально заявляемые классы: CHECKLIST, CONFIGURATION_MENTION, CREW_COORDINATION. Остальные классы должны поддерживаться схемой/обработчиком; научный вывод о них возможен только после независимой разметки и заранее объявленного расширения scope.

Test для NLP: минимум 20 независимых групп, 300 human-verified episodes/utterances, не менее 30 positive примеров каждого claimed label. Для salience — не менее 50 positive и 50 negative примеров. Эти данные могут совпадать с ASR test по записанным сессиям, но не с train/dev по группам.

На одинаковом human transcript input: macro-F1 trained classifier ≥ 0.80 и не менее чем на 0.03 выше rules baseline. Для итогового candidate ASR→NLP: precision значимых эпизодов ≥ 0.80, recall ≥ 0.85. В отчёте обязательно разложение NLP-only vs end-to-end и результаты на всех поддержанных labels.

При отсутствии temporal labels допускается отдельный `UTTERANCE_NLP_GATE`, но полный `TEMPORAL_EVENT_GATE` остаётся `NEEDS_MORE_DATA`. Нельзя переименовать utterance-метрику в temporal success.

### 14.4. Статусы и promotion

Статусы каждого gate:

- `PASS`: достаточные данные и все его условия реально выполнены.
- `FAIL`: измеренные условия/инварианты нарушены.
- `INCONCLUSIVE`: данные/запуск корректны, но неопределённость не позволяет подтвердить статистический эффект.
- `NEEDS_MORE_DATA`: нет достаточного независимого объёма или нужной разметки.
- `BLOCKED`: инфраструктура, лицензия или веса не позволяют выполнить проверку.
- `NOT_RUN`: проверка не запускалась.

Пустая таблица метрик или skipped tests не означают PASS. Отчёт отдельно показывает `implementation_complete`, `engineering_status`, `asr_quality_status`, `nlp_quality_status`, `temporal_event_status`, `validated_scope`, `deployment_candidate`.

`promote` назначает release candidate только при требуемых PASS и совпадении hashes. До этого inference доступен как baseline/research preview с понятной маркировкой, но утверждение «наш pipeline улучшил качество» запрещено. Возможность вручную просмотреть research candidate не должна обходить научную приёмку или подменять release pointer.

Если целевой эффект не достигнут: провести разрешённый dev error analysis, проверить другие варианты в установленном бюджете; по его исчерпании сохранить лучшую конфигурацию, все результаты и точный blocker/провал. Не менять baseline, эталоны, проценты или критерии. После финального неуспешного test новая оптимизация требует нового независимого подтверждения.

## 16. Надёжность, хранение и безопасность

В PostgreSQL: `sessions`, `audio_assets`, `processing_jobs`, `job_attempts`, `pipeline_runs`, `transcript_segments`, `events`, `review_revisions`, `model_versions`, `benchmark_runs`, `outbox_events`. Допускается JSONB для расширяемых результатов, но ключи, ownership, статусы и ссылки — типизированные поля/constraints. WAV/model binaries в PostgreSQL не хранить.

Job lifecycle: `QUEUED → RUNNING → SUCCEEDED | FAILED | CANCELLED`; дополнительно `cancel_requested`, stage и attempt отдельно. Общий результат может иметь `partial` для optional component без сокрытия его причины.

Обязательная надёжность:

- DB outbox для атомарного создания job и намерения отправить сообщение. Publisher/dispatcher можно реализовать в управляемом API background loop с транзакционной блокировкой строк, не добавляя новый сервис. Отдельный процесс допустим при обосновании.
- Persistent messages, durable queue, publish confirms и late ack с учётом Celery semantics [S9]. Доставка at-least-once: дубликаты ожидаемы. Не обещать exactly-once.
- Idempotency-Key + request hash; одинаковый запрос возвращает тот же job, другой payload под тем же ключом — 409.
- DB lease/heartbeat и fencing attempt token; повторная задача не создаёт второй журнал, stale attempt не перезаписывает результат нового. Уникальные constraints и atomic write/rename артефактов.
- Ограниченные retries только для временных сбоев; ошибку декодирования/прав доступа/конфигурации не ретраить бесконечно. После restart сверка expired leases и безопасное продолжение/повтор стадии.
- Progress отражает реальные стадии/processed duration, а не таймер до 100%. Cancel проверять между chunks; необратимые внешние действия отсутствуют.
- Результат стадии кэшируется по hash исходного аудио, эффективной конфигурации и model/stage version. Изменение VAD/model/glossary инвалидирует правильные downstream-артефакты.

Безопасность базового локального продукта: один владелец/документированная service authentication, API key из env/secret или серверная сессия для UI. Не внедрять ненужную многопользовательскую IAM, но не оставлять endpoints без контроля. Для cookie UI — HttpOnly, SameSite и CSRF для write; токены не хранить в localStorage и не отдавать в HTML.

No remote URL ingestion по умолчанию. CLI-import ограничен разрешённой директорией, запрещены path traversal, symlink escape и archive zip-slip. FFmpeg запускать через argv без shell, с лимитами времени/ресурсов и разрешёнными input protocols. Runtime не использует `trust_remote_code=True` для неизвестных датасетов.

Контейнеры — non-root, без privileged, Docker socket и host-network; `no-new-privileges` и ограниченные writable dirs. Секреты не в image/git/логах. Структурированные логи содержат IDs, timing, error codes, но не полные переговоры, персональные данные или audio bytes.

Удаление сессии удаляет derived files и review content по политике; запретить восстановление удалённых файлов поздним worker через tombstone/fencing. Резервные копии/retention описать отдельно, не обещать удаление из внешнего backup мгновенно. Получение согласия/прав на записи остаётся обязанностью владельца данных; приложение предоставляет manifest/provenance и локальную обработку.

## 17. Тестирование и воспроизводимость

### 17.1. Обязательные unit/contract tests

Аудио: повреждённый файл, тишина/нулевой RMS, короткий callout, clipping, разные sample rates, отдельные каналы, границы chunks и mapping к оригиналу. Размер/длительность и invalid JSON metadata.

Нормализация: `fifty` не превращается в `fifteen`; `tree` не становится `three` глобально; отрицание не исчезает; отсутствующая unit не выдумывается; исходный текст неизменен; CSV formula escaping и HTML XSS.

ML: baseline/candidate effective configs; внешний VAD без двойного внутреннего; no forced translation; chunk dedup сохраняет настоящие повторы; scorer получает все samples, включая failures. Отдельный тест подтверждает, что reference fields не могут попасть в AsrProvider.

Данные: split graph для speaker/session/variant, audio duplicates, frozen manifest tampering, train-only vectorizer.fit, отсутствие test в search/training, неразмеченный список не становится negative-label.

Метрики: вручную вычисленные S/D/I, пустой reference, корпусный WER, entity occurrence matching, неправильное число, отрицание, spurious entities, multi-label support, temporal duplicate predictions, paired group bootstrap со стабильным seed. Числовые fixtures синтетические и отмечены как тесты кода.

Quality gate: PASS/FAIL/INCONCLUSIVE/NEEDS_MORE_DATA/BLOCKED/NOT_RUN, baseline=0, недостающая страта, несоответствие hashes, невозможность promote без требуемых PASS.

### 17.2. Integration/E2E

Реальная БД и брокер; миграции на пустой и существующей БД; upload→job→result→review→export; повторный POST; повтор delivery; restart worker во время processing; недоступный broker; low disk; cancel/delete race; path traversal; отсутствие прав; concurrent reviews.

Минимум один реальный ASR smoke-test на маленьком разрешённом человеческом аудио с provenance. Моки допустимы для быстрого CI, но отдельный флаг `--real-asr` обязателен и не должен включать mock backend. Sine wave или TTS smoke не являются реальной ASR benchmark-выборкой.

GPU integration и pyannote integration запускаются только в соответствующей среде; отсутствие среды выводит явный skip/blocker и отражается в final report. Не заявлять, что Docker/GPU/доступ к корпусам проверены, если среда этого не позволила.

### 17.3. Артефакты каждого benchmark

`run_manifest.json`, `effective_config.yaml`, `environment.json`, `model_manifest.json`, `dataset_manifest.sha256`, `selection.lock.json`, per-sample predictions, raw S/D/I counts, metrics.json, per-sample.csv, group-metrics.csv, entity-confusions.csv, event-metrics.csv, timing.csv, gate.json, report.md и report.html.

Графики из реальных измерений: baseline/candidate WER с CI, WER по шуму/языку, critical entity errors, multi-label confusion matrices, quality/runtime tradeoff. При отсутствии метрик выводить «не измерено»; не рисовать демонстрационные улучшения в отчёте эксперимента.

Дерево — рекомендуемая организация, разумное объединение маленьких модулей допустимо. Не создавать десятки пустых файлов ради соответствия дереву.

CLI, вызываемый из tools/trainer/evaluator:

```sh
north55 doctor
north55 assets fetch --preset cpu-demo
north55 datasets inspect --config configs/datasets.yaml
north55 datasets import-local --manifest /data/input/manifest.jsonl
north55 datasets validate --manifest /data/curated/manifest.jsonl
north55 benchmark prepare --config configs/datasets.yaml
north55 benchmark dev --config configs/search.yaml
north55 train events --config configs/events_train.yaml
north55 train asr --config configs/asr_lora.yaml
north55 benchmark freeze --acceptance configs/acceptance.yaml
north55 benchmark test --selection /artifacts/selection.lock.json
north55 benchmark report --run-id <actual-run-id>
north55 promote --run-id <actual-passing-run-id>
north55 demo --real-asr
```

Это целевой контракт: разработчик обязан реализовать и протестировать эти команды либо явно описать минимальные совместимые изменения. `benchmark test` запускается в evaluator с отдельными reference mounts; он передаёт sanitized inference-задания через очередь существующему worker, у которого нет reference mount, и затем оценивает предсказания. Не монтировать всю .data целиком в worker: только audio-проекцию и необходимые модели. Benchmark-задачи не создают пользовательские журналы и reviews. Docker socket для оркестрации не требуется. Нужные для обучения/отчётов дополнительные YAML должны быть созданы, а не упомянуты без существующего файла.

Exit codes: 0 — успешная операция/PASS; 1 — runtime error; 2 — invalid configuration/data integrity; 3 — quality FAIL; 4 — NEEDS_MORE_DATA/INCONCLUSIVE; 5 — BLOCKED; NOT_RUN не может вернуть успешный quality-gate exit. Для команд, не выполняющих приёмку, код 0 означает выполнение команды, а не качество ML.

## 20. Что должно быть в финальном сообщении Codex

Краткая архитектура и расположение модулей; точные команды CPU/GPU запуска; какие реальные файлы и модели использованы и на каких основаниях; список реально выполненных тестов; baseline/candidate таблица только с полученными метриками; статусы engineering/ASR/NLP/temporal gates и область подтверждённого качества; доступ к результатам/отчётам; явные blockers/limitations и команды воспроизведения.

Обязательная формулировка при отсутствии доказательств: «Модуль реализован/частично реализован; улучшение пока не подтверждено по следующим причинам: …». Обязательная формулировка при успешной проверке: «На таком-то зафиксированном наборе и в таких-то условиях получено …; это не доказывает тот же эффект на всех реальных тренажёрных сессиях».

**Конечный результат задачи — работающий локальный модуль и проверяемые свидетельства его качества, а не обещание, что каждый добавленный ML-этап обязан улучшать каждую запись.**
