Текущее приложение — Go HTTP API на `net/http`, PostgreSQL через `pgxpool` и Redis
через `go-redis`.

## Авиакомпании и копирование структуры

Авиакомпании используют `users:read`/`users:write` и явные административные ID.
Создание без `copyFrom` добавляет стандартную шкалу из пяти оценок. Обе точки входа
копирования переносят шкалы, каталоги, библиотеки, контент и сценарии с новыми связями
и UUIDv4. Загрузка источника и все записи выполняются в одной транзакции; индексы
загруженных связей позволяют обходить граф без повторного сканирования всех строк.

## Библиотека элементов и папок

Первые 15 библиотечных маршрутов используют назначенные пользователю ВС;
административная роль сама по себе не заменяет эти назначения. Aircraft selector
сохраняет различие числового ID и строки, принимает код ВС и проверяет доступ.
Создание элемента без селектора выбирает первый назначенный ВС; для корневой
папки нужен единственный ВС либо явный селектор. Дочерняя папка наследует ВС родителя.

Сравнительные проверки включают полный граф до/после изменений, SQL-сбои,
сохранность frozen training, копирование созданной через API библиотеки и запуск
тренировки из копии.

## Блоки, параметры и состав

Девять маршрутов реализованы в `library_blocks.go`, `library_block_params.go` и
`library_block_elements.go`. Вложенный HTTP-контракт находится в
`library_block_validation.go`. Права различаются: список блоков требует
авиакомпанию, а создание/изменение блока и добавление/изменение его элемента —
ещё и назначенные ВС. Чтение и добавление элементов допускают архивный блок;
изменение и удаление элемента требуют активный блок.

Замена params сохраняет ID родительской строки, очищает прежние значения и удаляет
старые takeoff/landing rows. FK с SET NULL обнуляют ссылки других параметров на
эти же rows; детали взлёта удаляются каскадом. Новые TL получают новые ID, детали
взлёта сохраняются только для original TL. Параметры, состав и компетенции
обновляются одной транзакцией; SQL-сбой откатывает все связанные записи.

## Редактор сценариев и блокировки

Восемь маршрутов сценария дают полный список/детали, summary, создание, изменение,
архивирование, пометку удаления и восстановление. Список и все операции ограничены
авиакомпанией и назначенными ВС. Summary сохраняет поиск по title/code, SQL wildcard,
шесть сортировок и их camelCase aliases, clamp limit/offset, агрегаты модулей/дней
и первую привязку content-set label по ID связи.

Создание может связать сценарий с меткой набора контента; обе ссылки проверяются
по авиакомпании, ВС и принадлежности метки. Метаданные сценария не повышают
contentVersion. Даты без offset сохраняются как UTC; повторная запись того же
момента, в том числе с другим offset, не обновляет timestamp сама по себе.

DELETE переводит сценарий в архив. POST delete требует архивного статуса, сохраняет
deletedAt/deletedBy и удаляет edit lock одной транзакцией. Restore отвергает удалённый
сценарий; архивный возвращает в PUBLISHED при наличии publishedAt, иначе в DRAFT.
Особенность исходника сохранена: create/PUT со status=ARCHIVED может вернуть 404
после успешного commit при повторном чтении с фильтром активности. Тест отдельно
проверяет сохранённую запись, не принимает этот ответ за доказательство отката.

Три маршрута locks используют пару user/client-session. Захват/продление выполняет
условный PostgreSQL upsert, force разрешает перехват внутри доступного сценария,
release блокирует строку. Истёкшую блокировку может снять другой клиент. TTL задаётся
`SCENARIO_LOCK_TTL_SECONDS`, по умолчанию 60 секунд. Проверки с барьером БД охватывают
две попытки одного владельца, две вкладки, двух пользователей и принудительные
перехваты. В каждом случае остаётся одна строка с правильным владельцем. Её внутренний
ID может быть любым из двух одновременно выданных sequence значений.

## История версий сценария

Пять маршрутов revisions читают историю и полные снимки, сохраняют отдельную запись
или batch. Чтение допускает архивный сценарий; запись требует активного. Операции
истории сохраняют переданный снимок без изменения содержимого сценария и contentVersion.
Edit lock и expectedVersion применяются к отдельной операции snapshot.

Общая схема снимка воспроизводит значения по умолчанию, null, вложенные параметры,
числовые строки и guidance. Подпись считается по полной нормализованной модели
с ключами snake_case. Целые значения JSON за пределами int64 сохраняются точно;
канонический сериализатор принимает также big.Int, возвращаемый валидатором.
HTTP-ответ преобразует ключи в camelCase. Повреждённая сохранённая модель даёт
внутреннюю ошибку 500; проверка входящего payload сохраняет ошибки 422.

`createScenarioRevision` используется и редактором, и `ensureScenarioRevision` при
создании тренировки. Непустой clientEntryId возвращает прежнюю запись независимо
от нового содержимого. Без такого ключа выбирается последняя версия с той же
подписью. Новые номера выделяются под блокировкой строки scenario с повторной
проверкой дубля. Родитель может прийти позже ребёнка; восстановление parentRevisionId
ограничено тем же сценарием. Историческая action=ai остаётся меткой без обработки AI.

Pruning защищает последние 500 версий по clientCreatedAtMs/createdAt/id, ревизии
тренировок и всю цепочку parent/base/restoredFrom. Обход учитывает циклы. Новая запись с давним
clientCreatedAtMs может быть удалена при собственном commit: batch возвращает failed,
отдельный POST — 500 при повторном чтении. Тесты проверяют итоговую БД и неизменный
frozen graph. Конкурентные записи проверяются с барьером перед SELECT FOR UPDATE.

## Сохранение содержимого сценария

PUT snapshot проверяет права и область сценария, получает/продлевает edit lock,
затем условно повышает contentVersion при совпадении expectedVersion. Эти действия
и замена графа выполняются одной транзакцией. Отказ проверки, ограничения SQL или
commit откатывает также версию и блокировку. При двух запросах одной версии один
сохраняет изменения; второй получает конфликт версии либо блокировки редактора.

Существующие модули и упражнения сопоставляются сначала по clientUid, затем по ID.
Временные ID возвращаются в moduleIdMap/exerciseIdMap. Вложенность определяет родителя;
переданные scenarioId/moduleId внутри снимка его не переопределяют. Границы дней
вычисляются из dayIndex в порядке orderIndex/id, пропуски дней сжимаются. Служебные
виды упражнений очищают запрещённый состав; параметры и взлёт/посадка заменяются
с сохранением правил общих внешних ключей и нормализации guidance.

Удаление исходного содержания сохраняет frozen graph и историю тренировок.
Внешний ключ training_session.scenario_day_module_id обнуляется при удалении
исходного дня; day_index_snapshot и остальные сохранённые данные остаются прежними.
Ключи training_session_exercise_image защищают соответствующие файлы.

Очистка файлов выполняется после commit. Ошибка локального unlink возвращает 500
с уже сохранённой новой версией. Повтор запроса с прежней expectedVersion получает
409. Сохранение snapshot не создаёт запись истории автоматически; revisions остаётся
отдельной операцией клиента.

## Файловое хранилище

`internal/filestorage` сохраняет настройки FILE_STORAGE_BACKEND, MEDIA_UPLOAD_DIR,
FEEDBACK_UPLOAD_DIR, S3_BUCKET/S3_BUCKET_NAME, S3_REGION, S3_ENDPOINT_URL,
S3_FORCE_PATH_STYLE и префиксы media/feedback. По умолчанию используются относительные
каталоги uploads/media и uploads/feedback. Реализованы Open, PersistTemp, CloneImage
и Delete.

CloneImage сохраняет исходные байты, проверяет сигнатуру PNG/JPEG/WebP, предел размера,
вычисляет SHA-256 и создаёт новый UUID-ключ. Метаданные берутся из фактического файла,
а не из старой строки БД. S3-файл полностью скачивается перед проверкой изображения. Ошибка скачивания имеет приоритет перед ошибкой размера/сигнатуры.
Локальный fallback разрешён только при отсутствии S3-объекта. Ошибка доступа или сети
остаётся ошибкой. В режиме dual write сначала сохраняется S3-объект.

Пути нормализуются с проверкой компонентов `..`. Локальные символические ссылки
разрешаются, а удаление ограничивается корневым каталогом через os.Root. Каталоги
не удаляются операцией unlink. S3 использует официальный AWS SDK for Go с его
цепочкой credentials и [настройкой BaseEndpoint/UsePathStyle](https://docs.aws.amazon.com/sdk-for-go/v2/developer-guide/configure-endpoints.html).
При S3 или dual write выполняется удаление объекта; ошибка S3 допускается исходным
контрактом, после чего всё равно выполняется локальная очистка.

Unit tests проверяют реальные локальные файлы, ссылки, ошибки, подпись HTTP-запроса
и продолжение очистки после ошибки S3. Отдельные Go integration tests создают,
копируют и удаляют объекты в MinIO, проверяют байты, Content-Type, ETag, fallback
и dual write на размерах ниже, ровно на пороге и выше порога multipart. Изображения для сравнения
snapshot находятся в двух раздельных tmpfs volumes; оба API и harness видят
фактические изменения файлов. AI/speech storage не добавлен.

## Legacy редактирование модулей и упражнений

Каждая успешная операция повышает contentVersion один раз. Параметр
SCENARIO_REQUIRE_LEGACY_CONTENT_CONTRACT явно включает/выключает обязательные
X-Client-Session-Id и expectedVersion; без настройки они обязательны в prod.
При наличии expectedVersion ID редактора нужен во всех окружениях.
PUT различает отсутствующее поле и null: состав упражнения сохраняется при
отсутствии поля и очищается при null. Смена вида удаляет недопустимый состав.

## Чтение сценариев и проверка публикации

`assessment_scenarios.go` обслуживает четыре live-маршрута Instructor. Список
возвращает одну запись на день опубликованного сценария; anchor выбирается по
порядку связи, module_id и ID. Detail по имени, ID или дню строится из текущего
содержимого. Индивидуальные placeholders здесь сохраняются без подстановки истории
пилота. Frozen training использует отдельные сохранённые строки и не меняется
после редактирования или удаления исходного модуля.

`scenario_publication.go` читает подколонки связанных наборов контента и проверяет
готовность публикации. Оба обработчика требуют активный сценарий в области
авиакомпании/назначенного ВС. Подколонки требуют training:read, проверка готовности —
training:write. Требование с value=true закрыто, если в соответствующей подколонке
присутствует хотя бы один элемент требования из нужной авиакомпании и ВС.
Требование без подходящих элементов остаётся незакрытым. Операции не меняют
статус, версии, блокировки или содержимое; изменения редактора отражаются при
следующем чтении.

## Копирование сценария целиком

Изображения сохраняют исходный order_index; лимит числа изображений одного
упражнения к копированию сценария не применяется. PDF получают последовательные
номера, а их число проверяется до пропуска отсутствующих файлов. `ClonePDF`
разделяет чтение и сохранение с `CloneImage`, проверяет `%PDF-`, размер и хеш байтов.
Лимиты PDF по умолчанию — 20 файлов по 50 MiB, с отдельными переменными конфигурации.
Проверка MinIO включает multipart, fallback и dual write для обоих форматов.

## Должности и шкалы оценивания

Должности нормализуют пробелы и регистр для уникальности внутри авиакомпании.
Административный CRUD сохраняет исходные права и работу по явно заданным ID;
`/users/positions` требует только активного входа и читает свою авиакомпанию.
Эти два DTO различаются полем updatedAt. Пустой PUT, null и неизменившееся имя
сохраняют timestamps. Удаление проверяет назначения всем пользователям; отказ
сохраняет и должность, и профили. Переименование видно через общий auth/profile loader.

Шкалы оценивания сохраняют старые версии и значения. Административный API выбирает
следующий номер после максимальной исторической версии и позволяет создать первую
шкалу. Инструкторский API требует текущую активную шкалу и берёт её version+1.
Смена is_active, новая схема и её значения находятся в одной транзакции.
Значения вставляются пакетами по 1000 без дополнительного лимита на число оценок.

Компетенции и индикаторы сохраняют исходные коды с учётом регистра; удалённые строки
продолжают занимать код и участвовать в вычислении следующего order_index. Перестановка
перенумеровывает активные компетенции с нуля; пропущенные ID остаются после перечисленных
в прежнем порядке. PUT с прежними значениями сохраняет updated_at. Явный null доходит
до SQL; пустой код компетенции запрещён ограничением БД, пустой код индикатора разрешён.

Удаление компетенции одной транзакцией помечает её и активные индикаторы одним
retired_at, снимает связи упражнений, блоков и порогов flight types. Ранее удалённые
индикаторы, отчёты и снимки тренировок сохраняются. Обычные каталоги скрывают retired
записи, Commander продолжает показывать компетенции истории. Тренировка с замороженным
каталогом может завершить оценивание после удаления исходной компетенции.

Пользователи assessment используют общий auth loader для профилей, должностей и ВС.
Поиск сохраняет SQL-ранжирование по лицензии и имени, все слова запроса и порядок
при совпадениях. Без авиакомпании автора поиск остаётся глобальным, inactive пользователи
не отфильтровываются. Profile возвращает все отчёты последнего завершённого assessment,
включая повторы по компетенции, с текущими названиями справочников и сохранёнными оценками.
Это отдельная проекция от Commander. Null-поля исключены рекурсивно, пустые строки
сохраняются. `aiReviews` всегда пуст; таблицы AI/речи обработчик не читает.

Создание пользователя атомарно сохраняет User/UserInfo, при необходимости должность,
тип ВС и назначение ВС. Коды и имена нормализуются по правилам конкретного поля.
Повтор имени/email выбирает свободный суффикс; role возвращается в DTO, но не назначает
роль в БД. Временный пароль содержит 16 криптографически случайных байт в URL-safe
Base64; сохраняется Passlib-совместимый PBKDF2-хеш через общий auth. Обязательная смена
пароля и последующее отсутствие прав проверены через auth API. Ошибки в любой фазе
вставки откатывают все записи, включая ранее созданную должность.

Пример: runtime sync включает проверку writer и watermark, обновление runs,
добавление событий и обновление crew state. Все записи находятся в одной
транзакции. Если событие не проходит проверку, обновления runs тоже откатываются.
Повтор уже принятого запроса получает acknowledgement без новой записи события.

Создание тренировки записывает версию сценария, два assessment, snapshots упражнений,
каталог оценивания/Quick Comments и начальное состояние экипажа в одной транзакции.
Сохранённые snapshots остаются прежними после редактирования исходного сценария.
Повтор по `clientCreationId` возвращает сохранённый результат; другой payload с тем
же ключом даёт конфликт. Одновременные одинаковые запросы получают один результат.

Индивидуализация — детерминированный выбор блоков по длительности, истории оценок
пилота и результатам группы по должности. Она не вызывает модели или внешние AI API.
Ссылки на изображения и PDF сохраняются в snapshots.

Черновик v3 принадлежит логическому writer. Одинаковые revision/hash дают повтор
без изменения `updated_at`; старая ревизия и другой hash той же ревизии дают конфликт.
Переход полного payload → compact v1 → compact v2 разрешён без повышения ревизии,
если проекция старого payload точно совпадает с новым; понижение формата запрещено.
GET draft и список активных добавляют recovery context из сохранённого каталога,
шкалы оценивания и exercise snapshots.

Общий `/sync` использует ту же `syncRuntimeInTransaction`, что runtime endpoint.
Транзакция владеет блокировками training → crew state → draft и делает commit после
проверки runtime, черновика и ссылок на события/runs. Отказ черновика или отсутствие
ссылки откатывает все изменения. Legacy speech-поля остаются данными payload и хеша;
побочных действий для AI/речи нет.

Финализация заменяет итоговые оценки и наблюдения обоих участников в одной
транзакции. Значения шкалы и названия справочников сохраняются в snapshots.
Наблюдение TIMELINE связывается с конкретным захваченным событием; одинаковый
offset нескольких смен экипажа не заменяет эту связь последним событием.

Submit блокирует training и crew state, принимает pending runtime, строит
crew segments и проверяет canonical manifest до сохранения оценок и seal.
Квитанция читается из сохранённого состояния после commit. Повтор возвращает
ту же квитанцию, включая восстановление после перезапуска процесса; разные
ключи дают конфликт. Одинаковый ключ уже принятой отправки не переписывает
результаты новым содержимым повторного запроса.

Commander группирует завершённые тренировки по сохранённому сценарию и паре
участников независимо от перестановки их исходных слотов. Детали читают snapshots
и последние итоговые оценки. Для runtime-клиентов роли/длительности берутся из
проверенной sealed-цепочки и сохранённых segments; для исторических данных без
runtime используется явная проекция LEGACY_PLANNED. Повреждённая цепочка даёт ошибку.
Массив `aiReviews` остаётся пустым, обращения к AI/speech review таблицам отсутствуют.

Совместимость сравнивает точную сумму оценок двух пилотов с порогом; отсутствие
порога даёт compatible=true, заданный порог требует обеих оценок. `asOfDate`
включает весь день. Сводка показывает завершённые тренировки своей авиакомпании
с completed_at, историю по текущим названиям компетенций и сохранённым оценкам.
Среднее по должности отдельно выбирает последнее assessment с отчётами.
Агрегат ролей сводки повторяет проверки исходного summary; полная проверка цепочки
остаётся в detail. Для legacy сводка возвращает нулевое наблюдённое PF/PM время,
для sealed runtime — сумму сохранённых segments. Эти два режима не смешиваются.

Аналитика выбирает последнее оценивание отдельно для пилота, пары инструктор/пилот
или пилота/полугодия — в зависимости от маршрута. Пустое последнее оценивание
участвует в числе завершивших обучение, но не даёт оценок для распределения/среднего.
Текущая активная шкала определяет порядок, метаданные и нулевые buckets; неизвестные
исторические коды добавляются по алфавиту. Среднее по полугодию возвращается точной
строкой SQL avg без округления до четырёх знаков. Возраст считается на текущую дату сервера,
а `asOfDate` ограничивает историю полным днём. Пилотам требуется назначенное ВС,
инструкторам — наличие тренировки с их instructor_id; pilotId фильтрует оценивания
инструктора, сохраняя исходное число инструкторов.

## Наборы и матрицы контента

Обработчики матрицы используют таблицы `scenario_content_*`. Метаданные,
частичные обновления и вложенные ресурсы проверяют авиакомпанию и назначенные ВС.
Общий contentMatrixInput открывает транзакцию после проверки входа и доступа;
обработчик завершает её и строит DTO. При удалении подколонки FK модуля становится
NULL средствами PostgreSQL, без изменения updated_at модуля.

Summary считает labels в scenariosCount. Duplicate копирует структуру одним
commit, обходя дерево папок от корней; ячейки и связи со сценариями не копируются.
Смена ВС у копии сохраняет исходные element_id. Частичные PUT различают пропуск
и null: у меток/подколонок null orderIndex игнорируется, у папок/требований/связей
элементов попытка записи нарушает NOT NULL и откатывается.

## Ограничение запросов

`platform.Middleware` применяет CORS до ограничителя запросов, затем request ID,
security headers и маршрутизацию. `ENABLE_RATE_LIMIT` включает скользящие окна
60/1 секунд; Redis Lua проверяет и обновляет оба окна атомарно. Для Redis limiter
создаётся отдельное соединение с таймаутами 2 секунды и локальным fallback
после ошибки. Повтор подключения происходит через 30 секунд.
