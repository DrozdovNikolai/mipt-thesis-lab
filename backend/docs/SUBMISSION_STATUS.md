# Переход исторических статусов после удаления речи

Команда: `cmd/migrate-submission-state`. Это отдельная Go-программа; HTTP API её
не вызывает. Версия классификатора — `no-speech-submission-v2`.
Она меняет только исторические `WAITING_SPEECH`/`ERROR` в
`training_session`.

## Предварительный отчёт

Команда подключается только через явно заданную переменную
`NORTH55_MIGRATION_DATABASE_URL`. Адрес базы задаётся отдельно от DATABASE_URL приложения. По умолчанию выполняется `plan`, без изменений данных
или создания таблиц журнала. Чтение использует транзакцию и кратковременные блокировки.

```bash
bash scripts/go.sh build -o bin/migrate-submission-state ./cmd/migrate-submission-state
bin/migrate-submission-state -action plan > status-plan.json
```

В отчёте находятся ID, прежние значения строки, контекст оценок/runtime/речи,
целевой статус, причины отказа, выбранные `trainingIds` и `planSha256`.
Пустой `trainingIds` означает все подходящие исторические строки.
Отчёт может содержать тексты оценок;
его нужно хранить с теми же ограничениями доступа, что и выгрузку БД.
Реальные отчёты с данными пользователей не добавлять в репозиторий.

## Условия преобразования

- Есть `submitted_at` и две оценки разных участников с ролями cm1/cm2.
- Есть принадлежащая инструктору связанная speech session. Для ERROR подтверждён
  текст ошибки последней речевой сессии либо известная ошибка постановки речи в очередь.
- Завершённая тренировка имеет `completed_at`, непустые summary и заданный result
  обеих оценок. Новый статус — `COMPLETED`.
- Тренировка IN_PROGRESS действительно имеет незавершённые оценки и не имеет
  `completed_at`. Новый статус — `WAITING_ASSESSMENTS`.
- Если runtime существует, seal и ключи согласованы. Runtime capability >= 1
  требует сохранённый ключ квитанции в формате SHA-256. Старые записи без runtime
  допустимы с прежним явным ключом клиента или implicit SHA-256: исходный legacy
  submit сохранял такие ключи до появления runtime. При этом не должно быть
  crew events, exercise runs или crew segments без crew state. Квитанция и runtime
  этим переходом не создаются.
- `training.status=DELETED` остаётся заблокированным. Команда не восстанавливает
  удалённые тренировки и не выбирает для них новый статус по догадке.

Несогласованные участники/оценки, отсутствие связи с речью, неизвестное происхождение
ERROR и повреждённые реквизиты квитанции блокируют применение **всего отчёта**.
Команда не исправляет эти данные по догадке. Они требуют отдельного разбора и нового plan.
Полную целостность timeline/runs/segments дополнительно проверяет Commander; эта
миграция не заменяет проверку всех инвариантов состояния тренировки.

## Явный выбор записей

Если общий отчёт содержит строки, требующие отдельного решения, можно подготовить
отдельный plan для просмотренного списка ID. Остальные строки сохраняются и
продолжают появляться в общем отчёте. В выбранном наборе по-прежнему нельзя
применить план с хотя бы одной blocked row.

```bash
bin/migrate-submission-state -action plan -training-ids '<ID>,<ID>' > selected-status-plan.json
```

ID должны быть положительными, уникальными и существовать в БД. Порядок ID
нормализуется. Список входит в SHA-256 плана и сохраняется в журнале. Для apply
и его повтора передать тот же `-training-ids`; изменение или пропуск списка
прерывает операцию. Откат использует список из журнала и не принимает этот флаг.

План v1 нельзя применить командой v2: после обновления нужно получить новый plan.
Для уже применённого журнала v1 сохранить прежний проверенный бинарник: v2
отказывает в откате другой версии, поскольку формат проверяемого контекста изменён.

## Применение и журнал

Перед рабочим переключением остановить старые API/worker writers и клиентскую запись,
снять проверенный backup и получить итоговый plan в этом окне обслуживания.
Этот шаг нужен для согласованного перехода всей БД и клиентов, даже при наличии
блокировок отдельных строк. Перед применением выполните предварительный прогон на копии базы.

```bash
bin/migrate-submission-state -action apply \
  -run-id '<новый UUID запуска>' \
  -expected-plan-sha256 '<planSha256 из просмотренного отчёта>'
```

Для выбранного набора добавить `-training-ids '<тот же список ID>'`.

Изменяются только `submission_status`, `submission_error` и `updated_at`.
Оценки, подписи, timestamps завершения/отправки, хеши, seals, AI/speech записи
и файлы сохраняются. Речевые задачи не запускаются.

Применение создаёт две служебные таблицы Go-миграции:

- `north55_submission_status_runs`: UUID запуска, версия, хеш плана, выбранные ID,
  даты применения/отката;
- `north55_submission_status_changes`: полная строка до/после и исходный контекст для каждого ID.

Журнал и все изменения записываются одной транзакцией. Изменившийся planSha256
прерывает операцию. Повтор того же run ID и плана проверяет прежний результат и
возвращает `repeated: true`; он не создаёт новые изменения.

После применения повторить plan с тем же набором (ожидается пустой список), сверить количество/ID,
submit-status и Commander, затем проверить отображение статусов в клиенте.
Общий plan может сохранять blocked rows вне выбранного набора; они требуют
отдельного решения до выпуска.
Успех этой команды сам по себе не разрешает включение ещё не проверенных клиентов.

## Откат

```bash
bin/migrate-submission-state -action rollback -run-id '<UUID применённого запуска>'
```

Откат сначала сравнивает сохранённую строку и контекст с текущими данными. Если после
миграции изменили тренировку, оценки, crew state/events, exercise runs/segments
или речевую сессию, команда прекращает
операцию без частичного возврата. Она не перезаписывает более поздние правки.

При совпадении возвращаются прежние status/error/updated_at; журнал сохраняется с
отметкой отката. Повторный откат проверяется и не меняет данные. Откатанный run ID
нельзя использовать для нового apply: требуется новый UUID и свежий просмотренный plan.
