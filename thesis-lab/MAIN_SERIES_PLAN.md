# Зафиксированный план основной серии

Дата: 2026-09-16. Пилоты в results/pilot* исключаются из основных оценок.
Конфигурация фиксируется до первого основного прогона; версии файлов и образа
записываются рядом с сырыми результатами. При обнаружении дефекта стенда серия
сохраняется как незавершённая; исправленный запуск получает новый каталог.

H1: 6 повторов × 2 объёма UI-кэша (0, 16384 байта) × 3 профиля сбоев ×
3 варианта = 108 тренировок, по 12 наблюдений и перестановок. Каждый прогон
заканчивается двумя одинаковыми submit и проверкой результата в БД. Профили:
обычная доставка; локальное накопление и повторное открытие SQLite; настоящий
выход отдельного процесса после ответа HTTP до удаления outbox и его запуск
заново. Последний профиль включает стоимость запуска Python, а не измеряет
время запуска Flutter. JSON bodies учитывают UTF-8 и ответы, без TLS/заголовков.

H2: 6 повторов × 3 размера (5,25,100 упражнений) × 4 профиля × 3 варианта =
216 операций. Профили: успех; недопустимая ссылка во второй правке; остановка
между двумя запросами (для единственного snapshot — до отправки); устаревшая
версия после принятой чужой правки. Варианты: legacy CRUD без CAS, CRUD с CAS,
единый snapshot с CAS. Время сравнивается для успешного профиля, а не для
варианта, в котором запрос вообще не был отправлен.

H3: 1000,10000,100000 тренировок, 8 оценок на тренировку, до 1000 пилотов.
Для каждого размера: 2 набора фильтров (текущая дата / историческая граница),
1 или 8 параллельных клиентов, 6 повторных серий, 2 варианта и по 40 запросов.
Перед каждой серией — 3 прогревочных запроса. Историческая граница фиксирована
2020-01-02; меняющаяся селективность является частью опубликованной нагрузки.
Итого 5760 измеренных запросов. Сохраняются размеры выбранного tenant и таблиц
проекции; предыдущие tenant остаются в БД и учитываются при интерпретации.

Для средних и p95 использовать bootstrap по 6 повторным сериям. CI при таком
числе повторов ориентировочные; значимость не подбирать дополнительными
прогонами. Для корректности — число успехов/проверок и верхняя граница риска
при нуле сбоев; non-inferiority с узким допуском эта выборка не устанавливает.

Сравнивать варианты на двух backend из baseline/candidate worktree с одинаковыми
настройками и общей тестовой БД. H3 baseline выполняет неизменённую исходную функцию.
Для H1 исходный backend обслуживает split_full; для H2 — оба CRUD-варианта.
Перед основной серией экспериментальная БД пересоздаётся, пилотных данных нет.
Экспериментальные маршруты находятся только в benchmarks/server.py. CPU лимит
каждого backend/БД/runner — по 2 CPU; машина общая с другими задачами. Результаты не
являются capacity/SLA оценкой выделенного production сервера.
