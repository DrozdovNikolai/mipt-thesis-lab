# H2: доступ и подготовка к запуску в Cloud.ru

Дата: 14.10.2026. **Облачные эксперименты H2 ещё не запущены.**
Платные ресурсы в этой сессии не создавались. Этот отчёт подтверждает доступ
к части API и предварительный расчёт стоимости, а не результат гипотезы.

## Подтверждённый доступ

Локальный профиль прошёл IAM-аутентификацию. Секреты хранятся вне репозиториев
в `~/.config/firefly-thesis/cloudru/credentials.json`; в результаты не включены.
Project ID: `58c62bb5-2dd7-40d5-b279-c590544315d8`.

Проверки через API:

| Проверка | Наблюдение |
| --- | --- |
| Чтение проекта | HTTP 200, проект включён |
| Managed Kubernetes: список кластеров | HTTP 200, кластеров нет |
| Compute: ВМ, диски, SNAT-шлюзы, публичные IP | HTTP 200, списки пустые |
| Подсети | Одна существующая `Default_ru.AZ-2`, не создана экспериментом |
| Каталог Kubernetes | Доступны master 2 vCPU / 4 ГБ и worker 4 vCPU / 8 ГБ, 100% CPU, в `ru.AZ-2` |
| Billing consumption для проекта | HTTP 200, за проверенный период 14.10.2026 записей нет |
| Расчёт стоимости Kubernetes | HTTP 200, получены раздельные цены master, worker и SSD |
| Квоты организации/проекта через API v3 | HTTP 403: `dont have permissions to customers` |

Пустой ответ Billing не является сведением о текущем остатке гранта и не
гарантирует отсутствие ещё не отражённых начислений. Наличие конфигурации в
каталоге не резервирует физическую ёмкость.

Для диагностики также проверен документированный старый API квот:
`/v1/quota-usage` с фильтрами по проекту, каталогу и организации вернул
пустые массивы. Kubernetes `/v2/quotas/project/{id}` вернул `-1` для лимитов
кластеров и мастеров. Ни один из этих ответов не подтверждает достаточность
инфраструктурных квот Compute. Запрошена ручная проверка лимитов владельцем
в консоли; права сервисного аккаунта автоматически не расширялись.

## Предварительная конфигурация

- Один master: 2 vCPU / 4 ГБ, 100% CPU.
- Один постоянный системный worker: 4 vCPU / 8 ГБ, 40 ГБ SSD.
- Отдельная группа ASR: от 0 до 3 workers по 4 vCPU / 8 ГБ, 40 ГБ SSD.
- Зона-кандидат: `ru.AZ-2`; CPU-модель WhisperX и нагрузка из текущего H2.
- Основной генератор нагрузки размещается вместе со стендом. Внешний
  генератор из YC, если будет использован, образует отдельный сценарий.

Для четырёх рабочих узлов нужно как минимум 16 vCPU, 32 ГБ RAM,
4 ВМ, 4 диска суммарно 160 ГБ и 4 дополнительных сетевых интерфейса.
Для двух групп узлов требуются 2 группы безопасности и, при Cilium и одной
зоне master, 18 правил. Потребность в сети, публичных IP и балансировщике
проверяется отдельно. В группе с autoscaling квоты рассчитываются по
максимальному числу узлов, даже если начальное число равно нулю.

Это потребность эксперимента сверх уже занятых ресурсов, а не утверждение
о доступных лимитах. В существующей сети API показывает 4 интерфейса,
3 группы безопасности и 9 правил; они не принадлежат эксперименту.

## Исправление предварительной цены

В предыдущей оценке для master ошибочно использовался тариф рабочего узла
2 vCPU / 4 ГБ — 2,9768 ₽/час. Правильная цена зонального master такой
конфигурации — **8,601 ₽/час**. Она подтверждена API расчёта и строкой 42
действующего тарифа Managed Kubernetes версии 260918.

Все значения ниже — стоимость до применения гранта, с НДС по ответу API:

| Ресурс | ₽/час |
| --- | ---: |
| Master 2 vCPU / 4 ГБ | 8,6010 |
| Один worker 4 vCPU / 8 ГБ | 5,9414 |
| SSD 40 ГБ одного worker по округлённой ставке API | 0,6360 |
| Master + системный worker с диском, без ASR-узлов | 15,1784 |
| Master + системный worker + 3 ASR-workers с дисками | 34,9106 |
| Дополнительный ASR-worker вместе со своим диском | 6,5774 |

Шесть часов на максимальной конфигурации дают **209,4636 ₽ за перечисленные
вычислительные ресурсы и диски**. Это не полная стоимость стенда.
В PDF тариф SSD указан как 0,01586 ₽/(ГБ·час), API округляет его до
0,0159; для предварительного бюджета использована большая ставка.

Использован документированный, но помеченный deprecated метод
`POST /v2/billing/calculate-price-ext`: это расчёт, он не создаёт ресурсы.
В первой диагностической попытке параметр `rentPublicIpCount=1` не добавил
IP в возвращаемые `clusterAttributes`. Поэтому публичные IP не считаются
включёнными в эти итоги; повторный воспроизводимый расчёт явно исключает их.

Отдельные текущие тарифы для проектирования сети:

- SNAT-шлюз: 0,2074 ₽/час; его публичный IP: ещё 0,2074 ₽/час.
- Ресурсная единица Load Balancer L4: 0,80316666 ₽/час; IP балансировщика:
  0,2074 ₽/час. Обработанный входящий и исходящий трафик тарифицируется отдельно.
- Artifact Registry, базовый тариф: 0,00268071 ₽/(ГБ·час) хранения;
  условия исходящего трафика проверяются отдельно. Полное удаление слоёв
  образа может занимать до 24 часов с продолжением начислений за хранение.

При допущении одного SNAT, двух IP, одной ресурсной единицы балансировщика
и 2 ГБ registry фиксированная часть шестичасового окна составляет около
**218,05 ₽**. Это расчётная конфигурация, ещё не развёрнутая: метрики/логи,
трафик, фактические сетевые ресурсы и хвост удаления нужно проверить до
запуска. Предварительный бюджет пилота остаётся **500 ₽ до гранта**, окно
не более **6 часов**. Эта сумма не является технически установленным лимитом
списания. Cloud.ru-автоостановка ещё не реализована и не проверена.

## Выполненная разработка и проверки

- `h2/cloudru_access.py`: локальное хранение ключа и IAM-проверка.
- `h2/cloudru_preflight.py`: повторяемая проверка API, полный обход страниц
  Compute и кластеров, сохранение сырых ответов, расчёт цен без создания ресурсов.
- `h2/cloudru_manifests.py`: выбор системной и worker-группы через
  `mk8s.cloud.ru/node-pool-id`. Это поддерживаемая Cloud.ru метка для
  масштабирования из нуля. Пользовательские `firefly-role`/`firefly-trial`
  не используются как nodeSelector в этом адаптере.
- Ресурсы pod, taint-toleration, anti-affinity, очередь и настройки KEDA
  остаются такими же, как в исходном стенде. Разные UUID групп обеспечивают
  изоляцию постоянной системной нагрузки и ASR.

Команда проверки:

```bash
python3 -m unittest h2.test_cloudru_access h2.test_cloudru_preflight -v
```

Результат: **12 тестов прошли**. Проверены закрытые права файла, отказ от
перезаписи и перехода по symlink/HTTP redirect, отсутствие ключей в ошибках,
запрет изменяющих API-запросов в preflight, обработка неполной пагинации,
отказ выбирать sold-out flavor и неизменность политики KEDA после замены
nodeSelector. Это локальные проверки; они не подтверждают реальный запуск
Cloud.ru Cluster Autoscaler.

Воспроизводимая проверка доступа выполнена командой:

```bash
python3 -m h2.cloudru_preflight results/cloudru-h2-preflight-20261014-b
```

Выход `1` ожидаем для текущего состояния: единственная ошибка проверки —
403 при чтении квот; `provisioning_ready=false`. Повторять следует с новым
путём результатов, чтобы не перезаписывать наблюдения.

## Следующий этап

1. Получить реальные лимиты и занятое количество Compute и сетевых ресурсов.
2. Завершить Cloud.ru deployment/setup/trial adapter, полную смету и
   механизм остановки по абсолютному deadline; проверить права остановки.
3. Запустить отдельный облачный пилот и проверить автоматическое создание
   и удаление ВМ и дисков при переходах 0 → N → 0.
4. Настроить count-baseline, затем зафиксировать основную матрицу и критерии.
5. Собирать метрики и расчётные рубли вместе с отложенными начислениями
   Billing по уникальным ID ресурсов. Вывод о H2 делать только по основной серии.

Пока реализованы доступ, preflight и адаптация размещения pod. Старые
`cloud_ops.py`, `cloud_setup.py`, `cloud_trial.py`, `cloud_pilot.py` остаются
YC-специфичными и не должны запускаться как Cloud.ru deployment.
