## Что реализовано в первой серии

H1 сопоставляет существующие split/full, split/compact и unified/compact API
с одинаковой последовательностью доменных действий. Драйвер с дисковой очередью
имитирует доставку Instructor, проверяет результат непосредственно в БД и
выполняет повторную финализацию. IndexedDB настоящего Flutter приложения
проверяется отдельным браузерным тестом.

H2 сопоставляет существующие CRUD, CRUD с проверкой версии и атомарный snapshot.
В логической операции изменяются два упражнения; проверяются частичное
сохранение и перезапись чужой правки. Очередь Session имеет отдельный JS regression harness.

H3 добавляет экспериментальную проекцию аналитики в candidate backend:
`app/modules/commander/analytics_projection.py`, точку выбора SQL в
`app/modules/commander/service.py` и семь интеграционных тестов. Проекция
перестраивает факты затронутых пилотов, использует транзакционную очередь в
PostgreSQL, сохраняет историю и фильтры исходного endpoint. Установка таблиц
и триггеров выполняется только явным вызовом из стенда; стандартные маршруты
не переключены на прототип. UI Commander проверен отдельными браузерными тестами.

Таким образом, для H1/H2 выполнено сравнительное исследование уже имеющихся
механизмов проекта; новая серверная реализация этого эксперимента относится к H3.

## Повторение

Нужны Docker Compose v2, Python 3.12 с `matplotlib==3.10.5`, исходные worktree
и образ Python из `compose.yml`. Его SHA256 закреплён; версия и состав пакетов
сохранены в `provenance`. Образ уже присутствует на этой машине. При переносе
его можно экспортировать через `docker image save` и импортировать через
`docker image load`; один только локальный image ID не позволяет скачать его
с публичного registry. Исходный Dockerfile backend и зафиксированный список
пакетов позволяют собрать альтернативный образ, но это будет другое окружение,
которое нужно отдельно указать в результатах.

```bash
cd /mnt/c/DEV/startup/projects/firefly-thesis-lab
./run.sh all
# Или отдельная гипотеза с новой пустой экспериментальной БД:
./run.sh h3
# Заново построить отчёт по уже собранным данным:
python3 scripts/report.py results/main-YYYYMMDDTHHMMSSZ-all
# Проверить полноту матрицы и согласованность сырых измерений:
python3 scripts/verify_results.py results/main-YYYYMMDDTHHMMSSZ-all
```

Каждый запуск `run.sh` пересоздаёт только `thesis_bench` внутри compose-проекта
`firefly-thesis-20260916`. Не запускать две серии одновременно. Тесты backend
используют другую БД `thesis_tests`. Сеть внутренняя, порты backend/БД наружу
не публикуются, production `.env` не копируются. Подсеть стенда —
`10.253.216.0/24`; при переносе её нужно сверить с локальными Docker сетями.

Остановить только этот стенд, сохранив результаты и БД:

```bash
docker compose stop
```

Не запускайте `scripts/bootstrap.py` как способ обновления уже созданного
эксперимента: это скрипт первоначальной фиксации исходников. Для новой версии
исследования нужны новые ветки, worktree и каталог результатов.

## Интерпретация

Задержки получены на общей машине WSL2/Docker Desktop с лимитами по 2 CPU
для backend и БД. Данные синтетические, а сбои вводятся в заранее заданных
точках. Нулевые потери в конечной матрице не доказывают их невозможность.
Для исторических запросов и малых сценариев выигрыш может отсутствовать.
Результаты не являются измерением production SLA или физического телефона.
