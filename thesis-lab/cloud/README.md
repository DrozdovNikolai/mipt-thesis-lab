# Облачная репликация Firefly

Отдельное окружение для новой серии. Исходники основных репозиториев и завершённые
локальные измерения не изменяются. Облачная серия 03.10.2026 завершена;
результаты — [отчёт запуска](../YANDEX_CLOUD_RUN_20261003.md). Проверены существующие
CPU baseline для гипотезы №3: исходный SQL, оптимизированный SQL и проекция по пилоту.
Это ещё не проверка новой проекции по оценкам и не эксперимент с Kubernetes/GPU.

## Проверка доступа

```bash
python3 -m cloud.preflight --output results/yc-preflight-НОВЫЙ_ID
```

Скрипт только читает API: каталог, образ ОС, зоны, ресурсы, квоты, статус платёжного
аккаунта и его связь с облаком. JSON содержит время проверки и хеш плана.
IAM-токен используется в памяти, не записывается в отчёт и не выводится в терминал.
Баланс аккаунта не подменяет сведения об остатке и сроке гранта.

## Подготовка переносимого пакета

```bash
python3 -m cloud.bundle --output results/yc-bundle-НОВЫЙ_ID
cd results/yc-bundle-НОВЫЙ_ID
sha256sum --check --quiet SHA256SUMS
```

Пакет содержит рабочие версии файлов из экспериментального backend worktree,
измерительные модули, конфигурации и экспорт трёх существующих Docker-образов.
В манифесте записаны Git revision, хеш Git status, хеши каждого файла и image ID.
Имена `.env*`, ключи и служебные каталоги исключены. Выгрузка производственной БД
не используется: данные создаются синтетическим генератором. Экспорт образов
выполняется локально, облачные расходы при этом не возникают.

На сервере образы загружаются через `docker load -i images.tar.gz`.
Compose использует `pull_policy: never`, поэтому не подменяет образы свежими тегами.
Файлы с секретами создаются непосредственно перед запуском с правами `0600` и
не входят в пакет или отчёт. Пароли — случайные URL-безопасные строки:
`DB_PASSWORD`, `ADMIN_PASSWORD`, `JWT_SECRET_KEY`, `JWT_REFRESH_SECRET_KEY`.
В обоих Compose задаётся `SERVER_PRIVATE_IP=10.77.0.10`.

`compose.server.yml` сохраняет лимиты локальной серии: PostgreSQL и каждый backend
получают по 2 vCPU / 3 ГиБ. Порты 18000–18002 привязываются к частному адресу.
В группе безопасности доступ к ним требуется только от генератора нагрузки;
SSH разрешается с текущего внешнего адреса оператора. БД и Redis не публикуют порты.

`compose.loadgen.yml` запускает те же измерительные модули на второй машине.
`cloud.entry` заменяет только адреса HTTP и способ получения тестового пароля;
код измерений `expanded.reads` и `expanded.mixed` не меняется.
Общий WSL gate по нагрузке хоста отключён: для облачной серии нужен собственный
контроль нагрузки обеих ВМ. Старые критерии допуска нельзя молча применять к другой машине.

## Проверки перед основной серией

Проверка переносимого пакета выполнена 03.10.2026: 24 проверки корректности,
48 запросов чтения, 8 коротких сценариев смешанной нагрузки с 72 изменениями
и 64 чтениями, включая два сбоя обработчика. Ошибок чтения/записи нет.
Это функциональная проверка переноса в локальном Docker, не облачные бенчмарки.
Подробности — [YANDEX_CLOUD_READINESS.md](../YANDEX_CLOUD_READINESS.md).

Повторяемая проверка нового пакета:

```bash
python3 -m cloud.local_smoke results/yc-bundle-НОВЫЙ_ID \
  --output results/yc-smoke-НОВЫЙ_ID
```

Скрипт отказывается использовать уже существующий тестовый проект или старые
измерения. Создаёт отдельную непересекающуюся Docker-подсеть и удаляет только
свой тестовый проект и его том. Основные контейнеры не затрагиваются.

`render_init.py` подготавливает cloud-init с абсолютным сроком выключения
не позднее шести часов. Таймер устанавливается перед пакетами; при загрузке
после срока машина получает команду выключения. Проверены синтаксис и отказы
для недопустимых сроков/приватного ключа. На облачной ВМ фактическое выключение проверено, исходный срок после перезапуска сохранён.

Облачный smoke также пройден: 48 проверок корректности двух свежих наборов,
48 измеряемых чтений, 8 смешанных сценариев, 72 изменения и 64 чтения.
Основная серия отделена от smoke; её матрица зафиксирована в [CLOUD_H3_PLAN.md](CLOUD_H3_PLAN.md).

Оркестратор `cloud.run` выполняет стадии `setup`, `smoke`, `main`, `finish`.
Он отказывается повторять начатую основную серию и перезаписывать готовый профиль.
После сбоя нужно изучить сохранённые файлы и продолжить отсутствующие стадии;
удалять результаты и перезапускать всё под тем же идентификатором нельзя.

`cloud.ops` создаёт ресурсы по манифесту, проверяет принадлежность ВМ перед остановкой,
а перед удалением требует подтверждение локальной копии с проверенными SHA-256.
Гостевой таймер и внешний watchdog ограничивают окно шестью часами. При включении
таймера в раннем cloud-init требуется `--no-block`, иначе возможен цикл ожидания загрузки.
Остановка ВМ сохраняет платные диски: 160 ГиБ SSD — около 76,42 ₽/сутки.

В реальном запуске SSH выходит с другого адреса, чем HTTPS. Разрешение SSH должно
соответствовать фактическому исходящему адресу; широкие диагностические правила
не оставляются. Генератор доступен через `ProxyCommand` сервера по частной сети.
Приложения имеют два Docker-моста: внутренний для БД и обычный для опубликованных
частных портов. Один `internal: true` мост не обеспечил доступ с соседней ВМ.

`cloud.monitoring` публикует производные прикладные показатели; гостевой сборщик
сначала сохраняет сырые точки на диск. `cloud.costs` отдельно архивирует расчёт
выделенных ресурсов и предварительную детализацию Billing, включая зачёт гранта.
`cloud.export_monitoring` сохраняет ответы API для воспроизводимости графиков.
`cloud.analyze` проверяет полноту матрицы и строит отчёт, не изменяя сырые измерения.

Исходники оркестратора, фактические файлы обеих ВМ, изменения настройки сети,
версии ОС/контейнеров и хеши сохраняются в каталоге запуска. После основной серии:

```bash
python3 -m cloud.run finish results/ИДЕНТИФИКАТОР
python3 -m cloud.ops stop results/ИДЕНТИФИКАТОР
python3 -m cloud.ops cleanup results/ИДЕНТИФИКАТОР
python3 -m cloud.analyze results/ИДЕНТИФИКАТОР
python3 -m cloud.costs results/ИДЕНТИФИКАТОР
python3 -m cloud.export_monitoring results/ИДЕНТИФИКАТОР
python3 -m cloud.resource_report results/ИДЕНТИФИКАТОР
python3 -m cloud.cost_report results/ИДЕНТИФИКАТОР
python3 -m cloud.seal results/ИДЕНТИФИКАТОР
```

Удаление не затрагивает дашборд и локальные файлы. Копирование дампов проверяется
по хешам и читаемости TOC; это не заменяет контрольного полного восстановления БД.
После `seal` каталог результатов не изменяется. Проверка архива из его каталога:
`sha256sum --check --quiet SHA256SUMS`. Последующие сверки Billing сохраняются
отдельно, без перезаписи архивного `monitoring-writes.jsonl` и снимков расходов.

GPU-квоты проверяются отдельно. Нулевую квоту нельзя обойти запуском Kubernetes;
CPU-эксперимент не доказывает экономию GPU. Для гипотезы №2 необходимы реализация
контроллера, готовый обработчик и отдельный план сравнения с настроенным KEDA.
