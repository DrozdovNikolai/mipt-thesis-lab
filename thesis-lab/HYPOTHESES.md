# Формулировки для магистерской работы

## Гипотеза 1. Согласованная синхронизация состояния тренировки

Предполагается, что объединение доставки runtime-событий и компактного
оценочного состояния тренировки в одну операцию синхронизации между
firefly-instructor и firefly-backend уменьшает количество HTTP-запросов
и объём передаваемых данных относительно раздельной доставки runtime и
полного draft при сохранении корректности восстановления и финализации
в заданных сценариях повторной доставки и перезапуска.

Для отделения эффекта компактного представления от эффекта объединения
операций вводится третий вариант: раздельная доставка runtime и компактного
состояния. Во всех вариантах одинаковы доменные действия, дисковая очередь,
проверки конечного состояния и повторная финализация. UI-кэш варьируется
между 0 и 16384 байт; полный draft содержит реальные данные каталога.

Основные метрики:

- `SyncBodyBytes = Σ(bytes(request body) + bytes(response body))`, включая повторы.
- `SyncRequests = количество HTTP-запросов доставки`, включая повторы.
- `DeliveryTime = момент опустошения очереди − начало доставки`.
- `CorrectCompletionRate = корректно восстановленные и финализированные тренировки / все тренировки`.
- Число потерянных/дублированных доменных событий и комментариев.

В контрольных точках проверяются не только HTTP-коды, но и точные тексты,
идентификаторы, порядок событий и единственный результат повторного submit.
Измерения Python-драйвера не являются замером скорости Flutter приложения;
его реальное хранилище проверяется дополнительными тестами.

## Гипотеза 2. Атомарное сохранение версии сценария

Предполагается, что сохранение сценария firefly-session единым snapshot с
проверкой ожидаемой версии обеспечивает атомарность логической правки и
обнаружение конфликтующего сохранения. По сравнению с поэлементным CRUD
такой механизм снижает число частично применённых изменений при ошибке
в одной из частей и прерывании последовательности запросов.

Сравниваются три варианта: CRUD без проверки версии, CRUD с проверкой
версии на каждом запросе и один snapshot с проверкой версии. Это позволяет
разделить защиту от устаревшей записи и атомарность нескольких изменений.
Snapshot не обязан быть быстрее или компактнее точечной правки большого
сценария; этот компромисс измеряется отдельно.

Основные метрики:

- `PartialApplyRate = частично применённые логические операции / операции данного профиля сбоя`.
- `LostUpdateRate = перезаписанные принятые чужие правки / сценарии конкурирующей записи`.
- `ConflictDetectionRate = явно отклонённые устаревшие записи / попытки устаревшей записи`.
- `SaveTime` и `SaveBodyBytes` для успешных операций при 5, 25 и 100 упражнениях.

Логическая операция меняет два упражнения. Отдельно вводятся недопустимая
ссылка во второй части, остановка между запросами и принятая чужая правка
перед сохранением устаревшей версии. Для snapshot остановка между запросами
соответствует остановке до единственной отправки; этот профиль служит
проверке целостности и не используется для сравнения скорости.

## Гипотеза 3. Инкрементальная проекция для аналитики компетенций

Предполагается, что отдельная проекция актуальных оценок компетенций,
обновляемая по затронутым пилотам через транзакционную очередь PostgreSQL,
снижает p95 времени ответа распределения оценок в firefly-commander при
росте истории тренировок относительно исходного SQL-расчёта на чтении.
После обработки очереди проекция должна давать тот же результат, включая
tenant-фильтрацию, выбор последней оценки и исторический срез asOfDate.

Прототип сохраняет датированные факты оцениваний и последние версии
оценок; очередь публикуется в той же транзакции, что и исходная запись.
Обработчик поддерживает повторную доставку и восстановление после
прерывания транзакции. Сравниваются исходная и новая реализации одного
endpoint на раздельных backend с одинаковыми лимитами ресурсов.

Основные метрики:

- p50/p95/p99 HTTP latency и завершённых запросов в секунду.
- Отношение `p95_projection / p95_baseline` с парным bootstrap по сериям.
- `ResultParityRate = совпавшие ответы / проверенные комбинации данных и фильтров`.
- Время обработки изменённого пилота, возраст записи очереди до её обработки.
- Время полного построения и дополнительный размер таблиц с индексами.

Нагрузки: 1000, 10000 и 100000 тренировок, восемь оценок компетенций
на тренировку; один и восемь одновременно активных клиентов. Исторический
срез исследуется отдельно от текущего. Проверяются исправления оценок,
отмена завершения, повторное завершение, удаление, rollback, crash worker,
повтор задания и rebuild. Начальный результат имеет дополнительный
арифметический эталон, независимый от SQL обоих вариантов.

Эти эксперименты могут установить преимущество в исследованной нагрузке
и обнаружить контрпримеры; они не устанавливают автоматически ограничение
задержки обновления при непрерывном потоке записей или во всех production
условиях. Для внедрения проекции нужны отдельные миграции и включение
обработчика в эксплуатационную конфигурацию.
